## DuoFace .76 gap grounded in actual source, not assumed root cause

Current source sideplay/duoface-native-scene-host/DFSceneHost.m:
- Hosts an SBAppViewController using SBDeviceApplicationSceneEntity initWithApplicationForMainDisplay:, manually adds controller child, setsAutomatesLifecycle:NO, requests mode2; its video/fullscreen overlay belongs to the REAL app.
- Live ready frame is always 2×pane; child reference setters plus scene.updateSettingsWithBlock setFrame only; it does NOT explicitly coordinate per-app native12 renderSize policy, OmniCar-like scene orientation/background/foreground or SidePlay-like sceneFrameChanged restore.
- sceneSettingsBefore snapshot is saved at scene attachment but not restored in stop; committedReferenceSize becomes committed after selector dispatch, **without proof that actual remote app UIWindowScene and pixels accepted the change**. Source differences vs originals are proved, but don't conclude their unique role in SpringBoard's assertion.
- User already proved .75 hard-OFF FBScene setFrame regression boxed video and still crashed, so repeating that experiment is invalid. .76 restored original .74 geometry but **user reports video crash persists**. ## Prioritized mechanism (HYPOTHESES, not "fixed")

A) **Media scene-diff/lifecycle inconsistency**: YouTube/Facebook playing/fullscreen/rotation can change owned app scene settings; host independently forces a remote frame and wrong state combination may cause SBAppViewController assertion. The +440 locus plus playback report support prioritizing this, but NO .76 media event/readback/exception reason is provided.
B) **Scene generation/ownership/teardown**: stale handles or missing coherent frame rollback; SidePlay actually has both equal-frame guard and restore. In .74 first immediate crash there was no frame write, so any single-frame setter cannot explain all episodes alone.
C) **Loaded tweak interaction**: AppData, GhostBoard, OhMyRotate, other first-party QA modules present on old crash process; presence != cause. Isolation if needed must be controlled and only on parked iPhone, not uninstall/edit other projects.

External context (not DEB proof): https://github.com/pavunato/carsurf explains app-owned UIWindowScene and that rewriting a CarPlay template scene AFTER construction can throw; claims own separate iOS16 RootHide tests, not user's Dopamine. https://www.reddit.com/r/jailbreak/comments/1km0zo3/carbridge_freezing/ notes other CarPlay video fullscreen safe-mode incidents; anecdotal, not proof for DuoFace.
