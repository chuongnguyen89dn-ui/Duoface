## 3. Source trace: actual two separate failure-capable lifecycle gates (first-party)
1. `sideplay/duoface-native-scene-host/DFNativeHostAppDelegate.m:186–191, 237–264`: template-scene Heartbeat every 0.75 seconds only if `scene.activationState==ForegroundActive`. `sceneWillResignActive` unconditionally `stopTouchOwnerWithReason:@"scene-resigned-carplay-home"`; `sceneDidEnterBackground` also unconditionally stops. `sceneDidBecomeActive` restarts. **No separate observation of iPhone lock/unlock vs CarPlay Home**. A genuine CPTemplate transition caused by lock/interruption can tear down UI even when external screen is still connected.
2. `DFTouchOwnerProbe.m:285–307, 356–359`: SpringBoard watchdog treats a stale **2.5 second** app session heartbeat as inactive and `DFStopProbe` hides own windows immediately (`DFTouchOwnerProbe.m:252–261`). A temporary app suspend during phone lock can therefore blank DuoFace panes even without a clean CarPlay disconnect callback. This is a source-level conditional path, **not yet a demonstrated particular lock-trigger**.
3. `DFSceneLifecycle.m:39–75, 102–139`: `FBScene updateSettings:withTransitionContext:completion:` hook detects any owned live FBScene incoming foreground=NO and changes a mutable copy to foreground=YES (`corrected-copy=1`). It lacks an independent iPhone screen lock, external CarPlay activation, legitimate suspend, or phone-vs-CarPlay scene state gate. The separately hooked `SBAppViewController sceneHandle:didUpdateSettingsWithDiff:previousSettings:` consumes callbacks for owned manual scenes. **Actual log proves the foreground rewrite and callback consumption happen**, but does not prove the source of the background request or that the rewrite alone caused total black. A wrong foreground contract can plausibly leave remotely rendered scene/image and input out of sync during lock/restore; background transitions must not be globally overridden.
4. `DFNative12Chrome.m:1498–1526`: `appWindow.hidden` depends on startup/focus, and `v.userInteractionEnabled=loaded` depends on scene readiness. No code in this inspected part intentionally blocks a lower-half YouTube rectangle after lock, but the scene may look present while host/remote app input is unavailable. Chrome .118 removed the .116 root passive tracer/any-pane wake paths, so missing per-point evidence is expected.
5. `DFSceneHost.m` applies separate reference/frame and YouTube relay updates; older audit demonstrates host UIKit transform and FBScene geometry can commit asynchronously, yielding visual/input divergence. Lock transition supplies a specific new lifecycle hypothesis to test ahead of resizing.
