## Why .67 actually fails despite its successful logs

- Current `DFSceneHost.layoutScene` computes `logical=round(2×pane)`, sets `SBAppViewController.view.frame`, and applies a local transform. It logs `media-viewport-ui-only`.
- After stable hosting, v0.0.67 calls three-argument `setContentReferenceSize:withContentOrientation:andContainerOrientation:` on its private child and can return successfully (18 matched before/after logged on actual iPhone). **That call alone never proves remote UI size-class or scene.settings.frame changed**. User confirms all apps still render boxed. This is an actual device failure, not hypothetical.
- Original Native12 uses **multiple cooperating owners** and a remote scene settings frame. OmniCar also has explicit `sceneBox` and `setFrame` broker. DuoDash has process-boundary host request and UI host state. These common patterns support the **inference** that DuoFace lacks a complete remote-size/trait negotiation and acceptance loop; precise wrong field or initiating application is **not yet proven**.
- Actual SpringBoard `EXC_CRASH/SIGABRT` at `SBAppViewController sceneHandle:didUpdateSettingsWithDiff:previousSettings:+440` during the .67 session. AppData and OmniCarAppBridge show up in scene-update stack. They MAY interfere with DuoFace app scene updates; **cannot conclude which is causal from the stack alone**. This makes blindly enabling `FBScene.updateSettingsWithBlock:` unsafe.
- **Logo is physically PASS**; no gesture/axis/UI changes permitted in this workstream. Prior reports saying logo visually unverified are superseded by user's direct confirmation.

## Independent DuoFace architecture to implement AFTER proof

1. **Retain** existing `DFNative12Chrome` shared CPWindow + pane containers, logo/ratio, Zoom/Dock, menu/Style, app picker, IPC and diagnostic export. Do NOT reboot architecture or add another vendor host.
2. Write a **pure first-party policy module**, e.g. `DFAppViewportPolicy`, mapping `bundleID, preset, paneRect, usableScreen, focusedSlot, dockInsets, displayScale, appCapabilities` → `desiredRemoteLogicalSize, uniformDisplayScale, center, expectedFrame/orientation/sizeClass`. Reuse `DFLayoutEngine`, but do not invent individual app overrides or assume every app accepts landscape.
3. Add a **single per-pane session owner/transaction coordinator** inside existing `DFSceneHost`, not parallel to it. For every state change: capture current app/handle/generation, compute desired viewport, negotiate only supported child/scene APIs with exact ABI+ownership, then read actual `scene.settings.frame`, presentation bounds, orientation/trait and remote framebuffer if observable. State-machine `desired → requested → observed → accepted/rejected`; do NOT mark a setter return as acceptance. Never broadcast to all scenes or hook all FBScene globally.
4. Coalesce divider movement: scale local UI while dragging (never every-tick private scene mutation), commit at drag end or after stable transition, cancel stale work on Close/Swap/focus/Home/disconnect. Maintain ability to restore prior geometry safely only if exact owned scene/generation and setter contract are verified.
5. Strict **failure protection**: feature flag defaults to safe/no scene mutation until device read-only evidence establishes correct owner. Fail closed if collision/ABI mismatch, no repeated retries, no force-global landscape, foreground/unlock flags, and no hooking/altering OmniCar, AppData, SidePlay, DuoDash or DuoNavi license.
6. A single comparison log from existing integrated diagnostic captures per occupied slot: version, bundle, preset, pane and CP usable bounds, UI view/wrapper bounds, app reference-size, remote `scene.settings.frame`, orientation, safe-area/trait if available, focus/zoom, generation, owner, request/observation, crash timestamps. Capture read-only before any remote write code is enabled. Privacy: never collect video/account/location.
