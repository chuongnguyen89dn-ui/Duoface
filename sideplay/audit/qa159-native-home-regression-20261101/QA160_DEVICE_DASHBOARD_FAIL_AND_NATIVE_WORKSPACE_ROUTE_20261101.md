## New precise architecture comparison — source facts, not proof of causality
* Current signed QA160 `sideplay/duoface-native-scene-host/DFHomeStandalone144.m:298-306`: hook intercepts `DBDashboardHomeViewController iconManager:launchIconForIconView:`. When independently bridged, **does NOT call Apple's original native icon-launch handler**. Instead `DF144BeginSelectedBridge` writes a request plist and notifies SpringBoard; separate `DF144Solo.begin` creates `UIRootSceneWindow` on external display plus `DFSceneHost` to host `SBAppViewController`. App renders independently of native CarPlay workspace.
* `DF151WorkspaceOwnerCapture.h:DF151WorkspaceSnapshot` and real Log26 five examples show native `DBWorkspace` activeBundle=`com.apple.CarPlay.dashboard` and showingApp=NO, even while an independent app later receives a hosted-scene ACK. `DF152NativeWorkspacePrepare.h` when showingApp=NO calls `DF152ResumeNative(...,@"native-chooser-ready",...)` and does **not** call `DBMutableWorkspaceStateChangeRequest activateApplication:`. Current `DF147NativeDockSync147.h` alters native Dock and Home-button **displayState**, NOT `DBWorkspace` activation.
* On native Home press, `DFCarPlayOwnerObserver.h` calls `DF157NativeHomeCallbackObserved` → local `DF147Reset(@"native-home-stop")`, posts asynchronous SpringBoard SOLO stop, then calls original Apple `homeButtonUp:` exactly once. It never restores a native Home grid page controller; the **physical** device returns native Dashboard. Removing the SpringBoard overlay alone therefore **does not establish that Apple considers the just-closed scene an app in its workspace**. This is a concrete missing native activation step, *plausible cause*, not yet proven complete causal mechanism for dashboard routing.
* Genuine DuoNavi Observer3: original native Home callback locally `stopBridging/requestDismiss/bridgeDidDeactivate` before returning, with a CarPlay-side `CBBridgeManagerDashboard` state owner and SpringBoard `CBBridgeManager` dispatch. Original `activeBundle=dashboard` / showingApp=NO can also occur while its bridge is active; therefore **dashboard bundle readback by itself is NOT enough to prove the wrong page**. Observer4 verifies manager-owned `CBBridgedUIApp` factories. No original visible after-Home grid marker was captured. Never claim perfect original route parity.
* Independent public example (not imported, not licensed/copied into DuoFace): `https://github.com/pavunato/carsurf` (read project README, `sbtweak/CSCarLaunch.m`, `sbtweak/CSSceneManifestSpoof.m` on 2026-11-01). Their iOS16 technical route: native `DBApplicationController.sharedInstance applicationWithBundleIdentifier:` returns real app, native `DBMutableWorkspaceStateChangeRequest activateApplication:`, `DBWorkspace requestStateChange:`; LaunchServices typed entitlement **plus app-scene manifest/scene-role compatibility** supports real CarPlay `UIWindowScene`, not a standalone SpringBoard overlay. This is an engineering *candidate* for DuoFace, NOT a confirmed solution for this iPhone X iOS16.7.16 nor proof of original DuoNavi logic. Public project claims successful iPhone X iOS16.7.12, but that is its authors' claim and different jailbreak.
* Existing `DFHomeAdmission141.m` in DuoFace already implements selected iOS16 `LSBundleProxy entitlementValueForKey:ofClass...` and CarPlay policy/roster promotions. This **is not identical** to a complete real app-scene manifest/role contract or native `DBWorkspace` activation.
