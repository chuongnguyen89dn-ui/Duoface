# DuoFace .111 — CarPlay Home, YouTube rehost, splash, overlay teardown (2026-10-29)

## Evidence and original DuoNavi comparison

User verified on iPhone X / physical CarPlay that pressing CarPlay Home then reopening DuoFace remembers the app choices, but the YouTube pane is often blank until re-selected; the startup logo/progress replays on each return; and DuoFace chrome remains visible briefly over CarPlay Home. This is a **real device failure report for installed .110**, not evidence that .111 already works.

**Reference:** independently inspected Native12/DuoNavi original Debian audits, not copied vendor implementation/license:
- `sideplay/audit/native12-091-fullscan-20261028/COMPREHENSIVE_UI_FUNCTION_PARITY_VERDICT_20261028.md` explicitly maps Home cleanup to `CBWindow.destroyWindows / bridgeDidDeactivate`, splash to `CBSplitSplashScreenView.startLoadingAnimation`, per-slot persistence to `CBMultitaskingOverlayView.saveSlotIndex`, and scene app hosting to `CBBridgedUIAppView`.
- `sideplay/audit/native12-continuation-4888299/dismiss-ivar-owner/ORIGINAL_DISMISS_IVAR_OWNER.json` proves original `CBBridgedUIAppView.dismiss` IMP 0xaf01c owns `_appViewController` and `_wrapperView`; `dismiss-selref/ORIGINAL_DISMISS_SHARED_SELECTOR.json` confirms first `removeFromSuperview` receiver is `appController.view`. Exact second receiver runtime identity remains unverified. Those original routines cannot simply be substituted for first-party DuoFace.
- `sideplay/audit/native12-039-regressions-20261023/END_TO_END_ORIGINAL_APPBRIDGE_081_GAP_MATRIX_20261027.md` identifies the original host-side Live→foreground→app renderer state contract; a source-level scene-ready callback alone does not prove YouTube pixels rendered.
- Real first-party DuoFace implementation: `DFNativeHostAppDelegate.m` CPTemplate scene Home resign → `stopTouchOwnerWithReason` and session tombstone/notify → SpringBoard `DFTouchOwnerProbe.m` stop → `DFNative12Chrome.stop` clears views → `DFSceneHost.stopAllHosts` invalidates mode-2 SBAppViewControllers. A return therefore creates a new remote hosting lease, **not a resume of the old YouTube media scene**.

## Three causal fixes and their boundaries

1. **Blank YouTube on Home return:** Prior workspace stored an approved bundle but reopened via a single pending scene; `DFSceneHost.pollScene` accepts actual hosting/window/scene and may take up to 36 polls × 0.35 seconds (~12.6s), while Chrome gave up after 7 seconds, before the host's own timeout. `8d355c1184660c2b04c0fef9ebc2f85d31897932` introduces exactly one retry after failed scene/host creation, no synthetic ready; `7d8102814cd37057b2a22837226ddb83dabe71bb` extends the Chrome timeout to 13.5s, lets genuinely pending hosting complete, and records explicit `workspace-restore-skipped-allowlist-or-install` reasons. **Unverified on car:** even rehost success does not imply YouTube playback timestamp/state can be preserved after mode-0 invalidate.
2. **Repeated splash:** Previous `DFNative12Chrome.start` unconditionally presented a 1.3s startup window every Home→foreground. `335e04ba87532112d3463f90d7c57b403ba004fc` sets `sShownFirstSplashForPhysicalConnection` after initial launch; an actual detected physical unplug resets it, but CarPlay Home does not. On Home reentry the Chrome creates actual panes and begins saved-app restore without replaying startup animation. First physical launch still shows branded splash.
3. **UI lingers on CarPlay Home:** Previously `DFStopProbe` called DockZoomDetach and slow PID/scene host cleanup before hiding windows. `335e04ba...` factored `hideAllExternalWindowsImmediately`; `7d810281...` moves that conceal call to the **very beginning** of `DFStopProbe`, before Dock detach, PID inspection, and `stopAllHosts`, preserving native system Dock. Nothing here proves UIKit instantly delivers the Home resign notification on actual hardware.
