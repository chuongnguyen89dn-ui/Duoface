## What the original implementation REALLY does
1. `CBWindow.createWindows` @0xb1064 chooses `UIRootSceneWindow`, fallback `SBFTouchPassThroughWindow`, fallback `UIWindow`; dynamically creates `CBTouchPassThroughRootSceneWindow` and installs **three** independent `hitTest:withEvent:`, `pointInside:withEvent:`, `sendEvent:` IMPs via `class_addMethod` @b1380/b13c0/b1400.
2. Original window's dynamic `hitTest` @b2d50: checks `CGRectContainsPoint(window.bounds,point)`; within `carPlayUsableBounds`, consults current bridge and signals `noteUserActivity` before calling *superclass* hitTest; if super returns **the window itself**, returns `nil` rather than consuming an unclaimed touch. This is a CarPlay-specific **root-window input ownership** contract, not simply a transparent UIImage overlay.
3. Original dynamic `pointInside` @b2f00: first tests window bounds, then checks actual `carPlayUsableBounds`; outside ordinary root usable region it scans child views subject to hidden/alpha/userInteractionEnabled and converted hit point. This means touch ownership depends on actual subviews and frames, not an arbitrary percentage of screenshot.
4. Original dynamic `sendEvent` @b3144: examines a real `UIEvent` and its `allTouches`; signals current app `noteUserActivity` under its guard and then calls superclass `sendEvent:`, preserving natural event dispatch, not swallowing original app taps.
5. Separately `CBBridgedUIAppView.hitTest` @ac940 and `CBUIAppContainerView.hitTest` @b97cc notify activity then call super, and `CBTouchCloneView.sendTouchEventAtPoint:isDown:` @82d4c can synthesize IOHID digitizer/finger events after mapping view bounds to `UIScreen.mainScreen.bounds`. **This last mechanism is dangerous to assume belongs to normal CarPlay YouTube playback**: must verify creation/enablement/owner before considering it. Do NOT copy HID global replay into the independent app based on its existence.

## Our code, concrete deltas
- `sideplay/duoface-native-scene-host/DFNative12Chrome.m` creates generic `_externalWindowClass` for each real app physical slot via `initWithDisplayConfiguration:`, but does NOT dynamically install the original's window-level three-path touch ownership contract. It uses `DFNativePanePassthroughView.hitTest` passive observer with Began-event condition and a separate `DFNativeActivityObserver`.
- `DFSceneHost.m` uses `SBAppViewController` with a scaled (logical=round(2×pane)) view, deferred FBScene frame/reference transaction and only passive `DFSceneSurface.hitTest` observation; it has **no confirmed remote renderer per-point input ACK**. A cached scene-ready check or visible pixels are not proof the remote UIKit owner accepted a particular touch.
- `DFNative12Chrome.layoutControls` still assigns host HWND/pane geometry and controls; reading current code found no evidence sufficient to say a particular lower YouTube card is intercepted, clipped or mis-scaled. The photo cannot distinguish (a) another CarPlay UIWindow intercepting; (b) application local scene input region smaller than pixels; (c) mismatched physical-to-logical transform; (d) an internal YouTube gesture/UI condition. Do not call any one a proved root cause.
