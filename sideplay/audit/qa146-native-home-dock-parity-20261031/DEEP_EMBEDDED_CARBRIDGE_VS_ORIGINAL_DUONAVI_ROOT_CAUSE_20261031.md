**Confirmed distinction:** There are three different things:
1. Apple-sanctioned CarPlay app/scene entitlement: not present for ordinary unsupported iPhone apps.
2. **CarBridge** official proprietary product by leftyfl1p: Havoc version 2.0.15 supports rootless iOS13–16.7.16 (official listing); **its bytes/source have NOT been authenticated or analyzed here** and are **not present in our integrated package**.
3. **DuoFace first-party CarBridge-equivalent**, an independent SpringBoard app scene host and selected-app CarPlay admission/controller, compiled into `com.duoface.jb.embedded`. This is what the user wants. It exists but **is NOT yet behaviorally complete**. Do NOT say "official CarBridge installed in DuoFace", nor require the user to buy/upload another proprietary DEB to continue working.

### Existing package coexistence concern (not claimed reproduced)

Original DuoNavi control **Provides: com.leftyfl1p.carbridge13** and **Conflicts/Replaces** it, while remaining package identity `com.duonavi.app`. This proves original DuoNavi advertised a **CarBridge-equivalent virtual dependency**, not that it is the official CarBridge DEB. Our integrated DuoFace intentionally **does not** provide such a package alias. Not supplying a virtual package ID does not by itself prevent the first-party CarBridge-equivalent from operating; it can matter to unrelated external dependencies. An actually installed official CarBridge could also inject the same process, so concurrent use is a potential coexistence conflict to check, **not a proved device state**. Do not add `Provides` or a vendor conflict by conjecture or ship vendor code.
