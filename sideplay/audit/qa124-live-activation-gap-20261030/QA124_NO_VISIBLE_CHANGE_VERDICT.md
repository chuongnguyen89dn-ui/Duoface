## New important actionable finding: signed-package installation never reloads the running code

- Exact integrated package's `sideplay/jb-embedded-appbridge/scripts/postinst` (Git blob `6d576e0975473c2ea4f68f23807fd1d57982e21b`) performs **ONLY `uicache -p /var/jb/Applications/DuoFaceNativeHost.app`**, explicitly comments “No process restart”. It **does not restart DuoFaceNativeHost, SpringBoard or CarPlayApp and does not request a respring**. Original nativehost's `postinst` also only does uicache.
- Integrated package `sideplay/duoface-native-scene-host/build.sh` places SpringBoard-injected `DFTouchOwnerProbe.dylib` alongside the app executable; the `DFSceneLifecycle.m` hooks execute within SpringBoard. Updating on-disk dylib files does NOT replace a Mach-O already mapped into the running SpringBoard process. Updating on-disk native app executable does NOT replace already running `DuoFaceNativeHost` process.
- Therefore **one plausible and newly verified activation gap** is that QA124 was installed from Sileo but **not loaded**, because the installer does not restart existing processes. This is not a confirmed root cause on the user's device until process/runtime logging corroborates. The system might already have restarted automatically for another reason; never assert otherwise.
- The relevant *runtime* differentiator is the QA124 log line `qa124-scene-resign-retained-await-background` in `/var/mobile/Library/Logs/DuoFaceNativeSceneJoin.log` when the CPTemplate scene actually enters willResignActive. Sileo's version screen is **not** sufficient to prove it is being executed. The helper `Xuất log / lỗi CarPlay` in the iPhone DuoFace app exports this log plus `DuoFaceDeepTrace.log` and `DuoFaceTouchOwner.log`.
