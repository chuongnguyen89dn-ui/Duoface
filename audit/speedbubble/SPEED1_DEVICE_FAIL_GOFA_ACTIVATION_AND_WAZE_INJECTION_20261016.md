Exact `dpkg` error: `trying to overwrite '/var/jb/Library/MobileSubstrate/DynamicLibraries/GofaGMapHUDSource.dylib', which is also in package com.chou.googlemaps.vietmap 0.2.4`. Source: user screenshot. Previous public Sileo metadata/hash success **did not establish installability** on a device with another owner.
* **Different phone without TWHub**: Speed1 successfully installed, but Waze **exits and relaunches** repeatedly when used in the DuoFace split-screen. No iPhone crash report, Waze version, process backtrace or diagnostic log yet: **DO NOT assert which library caused the crash**.
* **No speed bubble appears** on CarPlay in real test. User correctly challenged missing start/enable/source controls.
* Until corrected and on-device verified, Speed1 **is not safe to represent as functional**. Known good fallback: exact Native12 SHA256 `85d754ea887eb8dd0659f65a5b2e3425564f617983937579753bad1a69433bf7`; do not use native13–21.

## Verified differences: user-provided real GOFAHUD 0.3.1 DEB vs DuoFace Speed1 source
* GOFA DEB SHA256 `62d6d818384844591217d74ab446404637127752e1b23bc1f9754ef1da297ad5`. Extracted local file `var/jb/Library/MobileSubstrate/DynamicLibraries/GofaCarplayGlobal.dylib`.
* **GOFA process injection:** `GofaCarplayGlobal.plist` has `Filter.Bundles = (com.apple.CarPlayApp, com.apple.CarPlayTemplateUIHost)`. This is **NOT SpringBoard**; phone SpringBoard has only separate helper `GofaLaunchHelper.plist`. In contrast `DuoFaceSpeedHUD.plist` is `Filter.Bundles = (com.apple.springboard)`. Do not confuse separate injection processes.
* Binary `llvm-objdump --macho --arch=arm64 --disassemble GofaCarplayGlobal.dylib`: `_Attach` at ARM64 `0xada0` examines window external display and `CPWindow`, `rootViewController`, `viewIfLoaded` then adds `GOFACarHUD` to that actual loaded CarPlay view and calls `refresh`; `_RefreshWindows` at `0xafd4` tracks `UIApplication.connectedScenes`, window pools and window changes, with periodic refresh and screen-connect. Verified `_InitializeCarControls` at `0x7e2c` registers Darwin control keys `local.gofahud.carplay.enabled`, `local.gofahud.carplay.gofa-active`, dispatch event `local.gofahud.carplay.show`, plus `UIScreenDidConnectNotification`. `GOFACarHUD refresh` ARM64 `0x89dc` checks HUD enabled/active control states before rendering. `pan:` at `0x9bd4` manages gesture and hide target. These are **genuine UI/activation/lifecycle controls**, unlike copying a pill style alone.
* `DuoFaceSpeedHUD` is a **new independent view**, not transplanted GOFA HUD. Current `runtime/speedbubble/DFSpeedBubbleBridge.mm` installs hooks on `CBWindow.show`, `resizeWindows`, `destroyWindows` in SpringBoard, attaches only when a hooked callback happens; it does not enumerate already-existing CarPlay windows, register a display-connect event or provide an explicit enabled state. `DFSpeedNativeHUD initWithFrame` sets `self.hidden=YES`; its `tick:` hides if `DFSpeedHUDReadBest` returns no fresh value. Therefore no sample => no visible bubble even if attachment succeeded. This UX makes activation untestable and may fail in startup ordering. Build/sign and public SHA PASS **cannot validate which class/method ran on device**.
* **GOFA's original trigger is not the DuoFace trigger.** User has no switch/source menu in Speed1; the code never sends a start/show command. Must add user-controlled enable/on + explicit source selection in **DuoFace** (Auto / Google Maps / Waze / VietMap / GOFA), and a visible placeholder state when enabled but data unavailable (e.g. “—”, not fake 0 or speed limit), to decouple **display visibility** from **data availability**. Need verify actual CarPlay host target and intersection with DuoFace Native12 scene and avoid duplicate HUD/windows or stealing CarPlay touches.

## Waze crash: suspected competing injection, not proven cause
* Speed1 installs TWO separate libraries into Waze: `DuoFaceSpeedSources.plist` bundle filter includes `com.waze.iphone` and its `DFSpeedAppObserver.mm` uses `method_setImplementation` on global `CLLocationManager.setDelegate:`, then `class_replaceMethod` on real delegate class callback `locationManager:didUpdateLocations:`. This method swizzle is global inside Waze's process and can overlap app/vendor hooks.
* Speed1 also embeds `WazeGMapHUDSource.dylib` from GMapHUD v0.2.3 and its `WazeGMapHUDSource.plist` injects into `com.waze.iphone`. Verified original upstream `bechou0410/gmaphud@v0.2.3/tweak/Makefile`: module comprises `waze-source.m`, **`waze-startup.m`**, `background-location.m`, `waze-output.m`, IPC. `waze-source.m` uses `MSHookMessageEx` with private version-guarded Waze 5.25.0 selectors and private GPS constructor and native limit reader (UUID guarded). `waze-startup.m` also contains guarded Waze navigation startup/retry and related hooks. **It is not a read-only publisher without behavioral hooks.** Two independently built Waze tweaks coexist inside one process: dangerous until device ABI and crash evidence collected.
* Collision with installed TWHub's `com.chou.googlemaps.vietmap 0.2.4` is deterministic for same file name/path, but **not evidence Waze app crash has same cause**, because Waze crash happened on device WITHOUT that package.
* Correct approach: isolate Waze from all new injection and confirm native12+HUD-only baseline runs Waze split; then evaluate ONE source adapter at a time and collect crash logs / Waze version. Do not force-overwrite files or declare `Replaces` on another package because it may break its owner or install behavior. Avoid bundling identical-named GMapHUD dylibs; namespace compatible integration or use safe external source in a device with that installed, without requiring users to install an extra tweak. Four sources still a goal, not proven.
