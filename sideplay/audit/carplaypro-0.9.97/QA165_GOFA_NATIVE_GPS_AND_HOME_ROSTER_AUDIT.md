# QA165 — nguồn dữ liệu GPS, native CarPlay Home và HUD độc lập (2026-11-01)

## User requirement
GOFA speed must use evidence-based real source; Google Maps/Waze/GOFA selected in DuoFace should be visible on native CarPlay Home like Safari was, and Speed8 bubble must stay visible above any live CarPlay application, Dashboard, and DuoFace panes. One DuoFace DEB, existing Sileo, no vendor license or proprietary binaries.

## Verified code causes
1. QA162–164 producer DFGofaSpeedSource162.m created its OWN CLLocationManager in GOFA process, not a GOFA internal feed. Its source requires location services + authorization + accepted GPS update; DFSpeedProtocol.hpp expires after 5 s, meaning no sample or suspended GOFA leaves speed unknown. It always sets limitValid=false. No real GOFA road limits/camera data implemented.
2. Native Home reconciler DFHomePublisher136Core.m bypasses FBS records already possessing a CarPlay declaration: if(already && DFHome141InfoHasDeclaration(already)) continue. This explicitly applies to native GOFA/Waze/Maps per Log19 comments. Safari instead has no native CarPlay declaration and is a separately authorized bridged app, so selected Safari is processed. Selecting native apps in DuoFace never proves Apple CarPlay Home icon added; actual native roster, capability, app installation, CarPlay customization and live logs matter.
3. QA164 Speed8 Chrome owns a compact external window only during DuoFace. Native CarPlayApp overlay is within that process UIWindow; standalone Safari or other bridged Home app is hosted in SpringBoard by DFHomeStandalone144.m and can occlude this native viewer. There was no Speed8 owner for that third, standalone window.
4. Original CarPlayPro Speed 0.9.97 static audit is unchanged, SHA256 e5b0918b3bc1948420f37a8a9e21365756da46fba44d582a3f2893aee9b4102f. SpeedAlerts.dylib filter includes CarPlayApp and source apps, selectors such as locationManager:didUpdateLocations:, cameraUpcoming and gofaAlertGroups, but static evidence does not provide true data-field contracts, nor prove GOFA limit/camera can be obtained by DuoFace.

## Native Home: actual Log19 and Log21 cross-check
- Previously uploaded **physical Log19**, archived in sideplay/audit/qa141-log19-declaration-map-20261031/LOG19_FINDINGS.json, has exact admitted-info class CRCarPlayAppDeclaration **22 samples each** for com.google.Maps, com.waze.iphone, and com.lumi.GOFA. YouTube (18), TikTok (22), WYN (18), Facebook (22), OpenAI (22) instead have nil. Thus native Maps/Waze/GOFA **already had** real declarations in that earlier device run; a developer-selected bridge algorithm should not recreate them like Safari. The finding is historical Log19, NOT current QA165 device status or current icon visibility.
- Real physical Log21 source sideplay/audit/qa142-log21-home-click-20261031/REAL_LOG21_HOME_ABI_AND_CRASH_VERDICT.md records **six selected nonnative Home icons visible**, while taps did not launch; QA141 had DB declarations readback and FBS newRecords=6. The classes/method encodings of iOS16 Home tap owner were measured. This proves selected-app bridge *can* create icons for apps lacking native declarations, and that registration ≠ launch.
- User now observes Safari visible and native Google Maps/Waze/GOFA missing. **Historical Log19 plus source early skip support a concrete explanation of disparate paths**, not proof that iOS CarPlay has intentionally hidden icons. Current CarPlay settings/installed state and read-only new QA165 roster logs required. We must not override genuine Apple CarPlay declarations or native Home policy based solely on old logs.
