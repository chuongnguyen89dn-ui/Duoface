## Historical Native12 / why gesture was present in source but not reliable on device

Original SHA256 `2fe8892c5ef8762e1e83b0fd6c4a029e25fc11758cc98fdbbb851bf6637e68ad` original `CBDividerView` has separate `pointInside:withEvent:` at `0xff728`, `hitTest:` at `0xff974`, `handleMoveButtonLongPress:` at `0x1005f4`, `moveButtonTouchUp:` at `0xffeb4`, and `handlePan:` at `0x10152c`. Original SHA-bound method crosswalk: `sideplay/audit/native12-vs-new-20261022/GESTURE_CALLSITE_CROSSWALK.md`. Existing independent historical `feature/visual12-duodash-recovery:src/DFDividerLogoGrip.inc` SHA `0b14c99ab8ed9283fbb8c98839eb5d0ebc70ad52` and `replacement/visual12/engine/runtime/DFINativeShell.inc` SHA `836eb52a51a309cf2d9740cfbcb22c407733f33d` use **0.30-second** hold; the CURRENT explicit user instruction supersedes it with **3.0 seconds**, so do NOT report original binary itself was proven 3.0-second. Correct functional semantics independent of hold delay: tap circular logo swaps, hold-drag along divider changes only relative logo position, dragging track perpendicular changes pane ratio.

Previously `DFNative12Chrome.m` already had `hold.minimumPressDuration=3.0` and `logoHold:`, so it is FALSE to say the function was missing in code. Concrete source bug: controlsVisible was `self.panActive || now<=controlsUntil`, with 4-second auto-hide timer; **during 3-second recognizer waiting, panActive stays false**, and finger TouchDown did NOT extend/lock visibility. A touch that begins with less than 3 seconds left on current hide timer could cause logo/window to hide and cancel the recognizer BEFORE 3s recognized. Source log until then only `logo-reposition-long-hold` after successful end; no start-state log. Current fix adds `logoTouchPending` from real `UIControlEventTouchDown`, retained in `BOOL controlsVisible=self.panActive || self.logoTouchPending ||...`, with cancellation/outside reset, 3s recognition logger, `logoHoldRecognized` latch preventing late TouchUpInside from swapping, and resets on CarPlay start/stop. Still uses original circular PNG `duoface-swap.png`, split ratio is never written in `logoHold`, position persist `saveSplitState`, horizontal/vertical along-axis logic unchanged. Source commit `458b3ec9b653434db3749fbbb690198747c14f26`.

## Media/scene source change (single-variable test candidate)

User's three real SpringBoard SIGABRT crash reports throw inside `-[SBAppViewController sceneHandle:didUpdateSettingsWithDiff:previousSettings:]`; exact violated assertion and installed DEB versions still unknown. The previous .37 baseline included `updateSettingsWithBlock:` scene frame updates, and .38 first added immediate UIKit `layoutIfNeeded` after those private updates. Source commit `bbcec6decc56783b4da077460e4d32a6bc4ea5eb` preserves the original-verified `setContentReferenceSize:` guards, Portrait=1, uniform geometry, input, 0.30-second debounce, `setNeedsLayout`, and scene `setFrame:` but **removes the new explicit synchronous UIKit `layoutIfNeeded` from within `commitSceneGeometry:`**, leaving UIKit to flush dirty views in the next ordinary layout pass. New trace `native12-layout-invalidated-deferred-no-sync-flush`. This reduces potential reentry during FBSceneMonitor notifications but **does not establish crash fixed**. It is candidate A from `MEDIA_VIDEO_CRASH_CROSSWALK_20261023.md`. Candidate B (scene frame mutation OFF) is NOT implemented in this version, to preserve single-variable diagnosis.
