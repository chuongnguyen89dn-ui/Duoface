# DuoFace Native Scene Host — isolated Stage B executable app

Source branch: `feature/duoface-native-scene-join-v1-20261020`.

This is a real UIKit application with independent bundle ID `com.duoface.native.scenehost`, a phone scene and an ordinary **CarPlay UIWindowScene role**. It does not claim CarPlay will admit it: iOS16 uses a private LaunchServices/CarPlaySupport entitlement/capability gate, requiring a distinct, ABI-gated and reversible admission implementation. This app alone does NOT carry an Apple-issued entitlement and merely declaring the role does NOT grant it.

The system must hand a `UIWindowScene` to `DFNativeHostCarSceneDelegate` before it creates `UIWindow initWithWindowScene:`. No manual Dock visibility, 45pt hardcode, FBSDisplayConfiguration, fake Dock, full-screen external SpringBoard window or image transport. The only CarPlay view is an honest placeholder that reports: “Chưa nối hai ứng dụng iPhone”. Stage C later integrates existing live V1BC scenes and real input, not this placeholder.

Status: BUILD CANDIDATE ONLY. Never publish this to public Sileo as a working DuoFace before private admission path and phone/CarPlay device safety have been verified. Does not modify current QA6, QA11, Native12, HUD8 or MyTweak recovery.


## 0.0.4~template1 — CarPlay Home **real scene admission** experiment (NOT device verified)
The original SidePlay 1.0.4 package audit includes a `CPTemplateApplicationScene` marker in its own iPhone app binary; earlier DuoFace NativeHost used ONLY the generic `UIWindowSceneSessionRoleCarPlay` role and never received a confirmed native icon/scene. This experiment adds a **separate genuine CarPlay navigation-template role** to the same independent NativeHost app, plus the exact jailbreak-signed `com.apple.developer.carplay-maps` key. The app still keeps the old ordinary UIKit CarPlay role for regression comparison. The added `DFNativeHostTemplateSceneDelegate` **only** runs if CarPlay provides a `CPWindow`; assigns a minimal no-interaction proof UI to that window and sets `CPMapTemplate` root. Does not use CarBridge/DuoDash/DuoNavi binary or license, does not open arbitrary apps, create a fake Dock or mutate system icon layout.

Important: `ldid -Sentitlements.plist` embeds a claim; it is NOT proof CarPlay accepts the entitlement on iOS16 jailbreak. The CPWindow surface in Apple's navigation model is map-only and isn't a generic interactive two-pane UI. This is a parked-car gate to decide whether a native CarPlay scene can be issued at all, not a claim the full DuoFace app has been delivered. Success criteria: system CarPlay Home icon visible → tap → log `native-carplay-template-scene-connected` and screen evidence → native Dock unchanged, no exitmode. Failure or safe mode: uninstall isolated package; no automatic respring. Native12, HUD8 and stable QA are unchanged. CI can prove code signing/packaging only.

## 0.0.7~cpbar1 — genuine CarPlay-owned control actions (unverified on device)

User reports the 0.0.6 UI still cannot be tapped. Root cause is architectural: Apple's CPWindow base view in a CPMapTemplate navigation app **does not accept direct taps or drag**; custom UIKit UIButtons and UIPanGestureRecognizers inside it are visual only. Sources: https://developer.apple.com/documentation/carplay/cpwindow and https://developer.apple.com/documentation/carplay/cpmaptemplate. Merely adding map buttons in 0.0.6 did not replace broken UIKit input. 0.0.7 places four persistent, named CPBarButtons in the CarPlay-managed navigation bar (App / Zoom / Style / Close) and three system CPMapButtons (33:67, 67:33, Swap). Their block handlers call the **same** independent Native12 controller actions as the legacy UIButton menu. It logs `carplay-system-bar-command-confirmed` or `carplay-system-map-command-confirmed` and updates the root status text. The two-slot UI is still placeholders; App does not launch an iPhone app. This does **not** restore direct touches on the drawn UI, the free-drag divider or arbitrary iPhone app input; doing that requires a distinct native-touch-capable presentation architecture. No SidePlay/DuoDash vendor code or license is bundled, no Dock manipulation or new SpringBoard hook. Code/CI must pass before publishing to Sileo. Only device testing can confirm the CarPlay button handlers on DiPlay.

## 0.1.0~native12ind1 — independent Native12 split UI on confirmed input owner

User physically verified that native `0.0.8` registered 8 CarPlay taps (`CHẠM OK 8` screenshot) and that `0.0.9` accepts the gesture QA controls on iPhone X/DiPlay. We preserve immutable public 0.0.9 and connect that first-party input owner to the complete source-owned Native12 **split UI/control layer**, not to closed vendor frameworks. Study references: `sideplay/native12-display/DFSPNativeFrame.m` and `DFSPNativeSlotPill.m` plus `sideplay/audit/native12-wiring-20261019/WIRING_REPORT.md`.

Code owns a single split ratio/focus/orientation state in the SpringBoard-only `DFNative12Chrome.m` and transmits session-scoped, monotonically numbered (2s freshness) commands to the CarPlay `DFNative12BasicController.m` renderer using existing protected `DFTouchOwnerProbe.m` / `DFNativeHostAppDelegate.m` contract. Native controls: two top-center pills with compact 64x19 or normal 76x22; restore state 72/80; centered thin split line and 28/30pt swap logo; dragging the divider/logo perpendicular adjusts ratio 1/3–2/3, 4% snap to 1/3, 1/2, 2/3 on release; 0.30s press-and-move along the divider relocates logo; swap changes slot labels; per-slot focus/restore; style rotates split left/right vs top/bottom; picker has rounded 20pt background and four icon-above-title actions App/Zoom/Style/Close. `App` and `Close` are scoped to the selected pane; **neither opens/closes a real iPhone app until scene-host module is delivered**.

Touch surfaces are individually bounded `UIRootSceneWindow` objects: two pill hit windows, one divider/grip window, one picker window (hidden unless active). No opaque full-screen input overlay is created, and the external screen Dock has a hard minimum exclusion inset; the native `CPWindow` only renders the two placeholder panes, never owns touches. Controls detach on scene disconnect; a 600s fail-safe prevents abandoned windows in case disconnect fails. None of this imports `SPDash`, `CBBridgeManager`, DuoNavi/DuoDash binaries, licensing or trial/watchdog code.

Testing gates: (1) macOS ARM64 iOS16 SDK compilation + signed rootless DEB + source-owned safety tests (2) Sileo GitHub Pages exact binary hash (3) physical device native pill, app picker, Zoom from *either* slot, split style rotate, logo reposition hold, swap and repeated divider pan; verify Apple Dock and reconnect/exit stability. Code/build and publication PASS do **not** imply hardware gate PASS. A genuine 2-app input host/picker is a separate subsystem and is explicitly not simulated.
