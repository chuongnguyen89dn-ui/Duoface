# DuoFace Gate0 — single parked-car forensic test, no Sileo and no Maps scene mutation

**Build branch:** `feature/duoface-gate0-onoff-readonly-20261107`, branched from signed QA182 code `bdd1116b5308869210a65b79b92b7d873fe4a04c` WITHOUT modifying the QA182, H1/keyboard, YouTube/GOFA, native Chrome, SpringBoard watchdog or integrated package.

**Deliverable:** separate private signed rootless DEB `com.duoface.carplay.gate0probe_0.0.1~gate0readonly1_iphoneos-arm64.deb` produced by workflow `.github/workflows/duoface-gate0-onoff-readonly-signed.yml`. **Never publish/replace main DuoFace Sileo package from this workflow.** Install locally only on the intended, parked test iPhone. No automatic respring, no settings edits, no extra background jobs, no scene reparenting or input interception.

## What this build actually implements
- **CarPlay/CarPlayApp**, **Preferences** narrowly filtered via `DFGate0CarPlayProbe.plist`; no SpringBoard injection.
- Records actual iOS runtime method type encodings of the native Dashboard presentation/scene frame/safe area/dismiss/layout/appear/Home/destroy entry points. Hooks ONLY `DBDashboardRootViewController presentBaseViewController:animated:launchSource:completion:` IF runtime argument types match; forwards original unchanged exactly once and records an entry timestamp plus original-return receipt **only for Google Maps**. A missing ABI is logged and no hook is installed. Does not call or swallow the completion block.
- Observes external `DBApplicationSceneViewController` + `FBScene` of `com.google.Maps`, scene ID, CarPlay window role and parent; never creates, launches or resizes a native scene. Absence of a scene in a snapshot does **not** prove iOS forbids scene creation.
- **OS source discovery**: reads only bounded CarPlay-related `.plist` candidate files in mobile SpringBoard/Preferences/CarPlay locations, up to 1 MiB/file and bounded folder enumeration; emits no raw filenames, car identifiers, other app lists, or raw preference dictionaries. Instead records candidate file digests, file kind, Maps-present boolean and *hashed map property-list locations*. These are **candidate** signals; they are NOT an authoritative per-car CarPlay Customize ON/OFF source.
- Every event includes source status `UNVERIFIED` and `stockSettings=UNKNOWN` until exact on-device source, active paired-car context and ON→OFF→ON calibration have been verified. Unlike QA182, it collects enough **raw source evidence** for that calibration instead of hardcoding only the final field. It intentionally does **NOT** turn a guess or human run label into verified ON/OFF.
- Independent Python `analyze_gate0.py` groups logs only by matching **verified** source and car-profile digest and excludes unknown/stale/conflict records. Includes negative regression tests; an official Gate0 PASS requires additional ON/OFF reader validation on the phone.

## One complete parked-car sequence (single DEB, no new rebuild between phases)
1. **Before install**: preserve current published DuoFace/QA182 version, take a rollback reference, park with parking brake on. Get the signed DEB and `CI_RESULT.txt` from the successful GitHub Actions run. Confirm DEB SHA256 against `SHA256SUMS.txt`; install locally only, not through public Sileo repo. Reconnect CarPlay or reopen the relevant processes so the new injection loads.
2. **ON**: in iPhone Settings → General → CarPlay → **the exact paired car** → Customize, confirm Google Maps appears/enabled; record a photo of this UI and a clock/time marker. Disconnect and reconnect CarPlay (Apple applies icon-state changes on subsequent connection). Launch native Maps from actual CarPlay Home app icon if present; additionally choose Maps inside DuoFace while the two-pane UI is active. Record the visual screen (actual map tiles vs stock Dashboard vs DuoFace pane).
3. **OFF**: hide/remove Google Maps from **that same car** in Customize. Record photo/time. Disconnect/reconnect. Do NOT launch from a nonexistent stock Home icon; request Maps from the DuoFace picker. Observe native scene creation in CarPlay process, not a phone scene. Preserve wrong/failed state rather than forcing ON.
4. **ON again**: restore Google Maps to its original Customize position and reconnect, ensuring original paired-car configuration restored. Repeat one native stock launch and one DuoFace selection so source behavior can be compared ON→OFF→ON.
5. **Export** exact three process logs if present: `/var/mobile/Library/Logs/DuoFaceMapsGate0-CarPlay.jsonl`, `...-CarPlayApp.jsonl`, `...-Preferences.jsonl`. Empty/missing files are evidence of injection or permission failure, NOT a passing test. Also retain the original DuoFace audit export and screenshot/time sequence (redact any vehicle name, account data or personal location before sharing). If `presentBase` runtime ABI is absent, event must remain unobserved, not manufactured.
6. **Analyze offline** (repository root): `python3 sideplay/gate0-carplay-maps-probe/analyze_gate0.py PATH_TO_CARPLAY.jsonl PATH_TO_PREFERENCES.jsonl --output gate0-verdict.json`. The analyzer will report **MEASUREMENT_BLOCKED** until a concrete OS source has been **separately validated and emitted with status VERIFIED and a matched per-car digest**. Do not substitute screenshots or user-entered labels into `stockSourceStatus` to get a fake PASS. Screenshots are external calibration corroboration, not the reader.
7. **Acceptance decisions**: only after OS source ON/OFF is validated **on this vehicle** can the actual native scene YES/NO under OFF be concluded. If OFF creates genuine native CarPlay Maps, proceed to own native Dashboard presentation transaction + fresh watchdog lease. If the OS blocks native scene under OFF, mark hard technical blocker and investigate real eligibility; never use phone Maps to claim native success. Full product gate still requires OFF, map pixels, hit testing/navigation, second app sustained and real CarPlay Home app grid.

## Scope / safety status
This private probe is **not** a replacement fix for QA182. It is observational and leaves current Home/scene/window controls in place, but injecting a third-party diagnostic into Apple's CarPlay process is still inherently risky; test only parked with immediate local uninstall path available. No iOS16 hardware validation can be claimed from macOS CI compile/sign alone. No original OmniCar/DuoNavi vendor code or license logic is used.
