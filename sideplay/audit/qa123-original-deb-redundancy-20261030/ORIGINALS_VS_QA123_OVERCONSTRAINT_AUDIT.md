## Core verdict — user's 'we added too much' hypothesis is substantially supported in *current source*

### O1 — Highest-priority over-constraint: CPTemplate owns the whole UI's lifetime, and immediately revokes it on ANY resign
- `DFNativeHostAppDelegate.m:248-254`: template `sceneWillResignActive:` **always** invokes `stopTouchOwnerWithReason:@"scene-resigned-carplay-home"`; `sceneDidEnterBackground:` likewise stops. The reason string **presumes Home** but callback itself cannot distinguish phone lock, a temporary background state, or pressing CarPlay Home.
- `DFNativeHostAppDelegate.m:185-194`: 0.75s heartbeat `renewTouchOwnerHeartbeat:` revokes session if `activationState!=UISceneActivationStateForegroundActive`; this is **another path for the same event**.
- This is a current-source FACT, not an assertion that iOS definitely sends resign on this user's physical lock. A Home-only gate was replaced by an over-broad lifecycle gate. A supported original DuoNavi/Native12 bridge uses physical CarPlay display and `CBBridgeManager` connection/window/pane-owner state for its bridge lifetime; original does **not** prove that arbitrary CPTemplate resign means disconnect/Home.
- **Risk:** app panes all black, Apple-owned Dock survives. **Do not simply delete callbacks**: would regress genuine Home exit.

### O2 — Second independent automatic teardown repeats O1 in SpringBoard
- `DFTouchOwnerProbe.m:397-421`: `DFWatchdog` checks file `Active`, session UUID, pulse time; stale >2.5s or revoked immediately calls `DFStopProbe(@"inactive-or-stale-heartbeat")`.
- `DFTouchOwnerProbe.m:364-395`: `DFStopProbe` immediately `hideAllExternalWindowsImmediately`, detaches Dock zoom ownership, stops Chrome/host; start/stop Darwin notifications are another path. Coupled with CPTemplate stop-tombstone this forms **two stop owners**, one triggering the other. The 0.5s watchdog is a backup, not proven sole defect.
- Difference: Original DuoNavi CBBridgeManager `handleCarPlayConnectionChanged:`, `carPlayUIScreen` / CADisplay, `CBWindow` and auto-resume handle real connection transitions. Nothing in original signed proof justifies treating one stale local CPTemplate heartbeat as physical CarPlay disconnection.
- **Refactor target (not yet done):** one independent decision owner for **physical disconnect / genuine Home / paused phone lock**, with other modules as consumers of that state. Keep fail-safe if host dies, not unconditionally tear down a still connected app during short lock transition.

### O3 — QA123 'rescue' itself depends on the thing O1/O2 destroy (circular prerequisite)
- `DFSceneLifecycle.m:147-184`: `DFSessionOwnsLiveCarPlay123` rejects pulse missing, inactive, >**1.65s**, off-main, or no extra UIScreen; then `DFIsOwnedHostedLockScene123` also requires exact manual current scene, `isHostingAnApp`, and a visible attached UIWindow.
- `DFSceneLifecycle.m:183-222`: the TWO under-lock replacements only return NO when **all** above are already satisfied, otherwise original Apple implementation. If phone lock tears down CPTemplate or detaches hosted window, the 'rescue' deliberately fails closed. It cannot resuscitate the already-revoked UI.
- Source result: logically **circular dependency**, verified. Physical occurrence not yet correlated. Multiple conservative gates all at once can overconstrain and eliminate the very lock transition being fixed. Original DuoNavi's three registered under-lock methods inspect bridge/selected-app/scene-host identity; no evidence that original uses DuoFace's CPTemplate heartbeat <1.65s or requires its hosted view be visible *after* lock.
- Do **not** broadly return NO for foreign apps or bypass phone passcode. Replace the circular condition with independently verified CarPlay connection + exact hosted-scene/session owner before transitions, preserving original iOS IMP fallthrough for other scenes.

### O4 — More than one foreground/lifecycle writer with no single transaction owner
- `DFSceneHost.m:529-548` sets foreground YES / backgrounded NO only on changed frame, while `DFSceneLifecycle.m:52-89` modifies foreground=NO incoming scene settings and `DFSceneLifecycle.m:183-222` adds under-lock decisions. `DFSceneHost.m:659-690` separately polls foreground and host/window ownership.
- Original DuoNavi `CBBridgedUIAppView.refreshSceneLayout` and `updateSceneSettingsFrame` plus `CBBridgeManager.renderSizeForBundleID:` coordinate the same frame / reference size / foreground / lifecycle ownership; Native12 additionally has three under-lock callbacks including **`interceptUpdateForScene:withNewSettings:`**, and scene update/apply/destroy hooks. QA123 only adds two lock decision hooks while keeping its pre-existing independent foreground-update pathways; no proof of equivalent one-transaction semantics.
- **Refactor target:** one per-scene generation/owner state machine; stop issuing independent corrections on each symptom. Preserve validated .90 YouTube orientation.

### O5 — Legacy test subsystems are still shipped next to the new host; potential competing window owners (conditional)
- Signed QA123 package `PACKAGING_PROVENANCE.json` includes legacy `DFV1APreflight.dylib`, `DFNativeDashboardBridgeQA.dylib`, `DFFirstPartyAdmission.dylib` alongside `DFTouchOwnerProbe.dylib`, Dock owner, map and YouTube relay. `sideplay/mytweak-independent-v1a/MTBridgeCoordinator.m:75-154` can create a **second** external `UIRootSceneWindow` when explicitly enabled, while modern `DFTouchOwnerProbe.m` owns 4 physical-slot windows. `sideplay/mytweak-native-bridgeqa/DFCPNativeBridgeQA.m:445-455` installs a 1s poll and separate experimental Dashboard owner but only when `MTCPBridgeExplicitOptIn()` is true.
- **Proved:** redundant *packaging/architectural paths*, not that they are concurrently live. Both old paths are normally off by opt-in; no device config evidence that they caused current black. An audit can safely **inventory** effective active modules/processes and configs before considering disabling/removing them in a separate build.
- Original DEB count alone is NOT evidence of defect. Original Native12 also has multiple dylibs and original DuoNavi injects multiple processes.

## Decision, no guessed patch / reproducible next task

**Most plausible root of unchanged QA123 black panes is excess lifecycle guards/duplicate teardown, not yet an empirically proven missing third lock hook.** Existing QA123 static unit tests only assert presence of selector strings and guards, not actual lock→Home transition discrimination. A binary compilation/pass cannot validate cross-process heartbeat lifetime.

Keep fail-safe disconnect/home and original IMP nonowners. Do not use undocumented passcode activation bypass, alter device security or force brightness.
