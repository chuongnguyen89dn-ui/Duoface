### Why that difference matters to the user's symptom

The six-DEB comparison proves a **real missing subsystem**, not an inference from license methods or number of dylibs. Native12 and DuoNavi original executable code **explicitly** toggles actual BKS screen blanking both ways; other adapters at least resolve/cache the same BKS API. DuoFace QA130 has only a system-idle assertion, which is a **different API with different semantics**. Therefore previous QA121 system-idle and QA130 owner-only fixes never implemented the original phone-screen blank/unblank policy, so it is technically expected **they do not reproduce the dim-main-display behavior the user sees in original tweaks**.

**Important distinction**: `BKSDisplayServicesSetScreenBlanked(0)` means a request to **unblank** the main display, not a request for a particular dim-brightness level or a way to bypass phone passcode. A dim display may be due to iOS lock UI, low brightness, native bridge scene policy, or a combination. These original **static code paths** do not prove that BKS *alone* makes remote YouTube Play work; DuoFace may still lose app foreground or remote touch event delivery under lock.

Also original Native12 / DuoNavi have scoped `SBSuspendedUnderLockManager` policies AND audio-only background handling, while DuoFace has an independently guarded subset. Screen unblank, remote scene foreground, touch events and frame clock are separate properties; **do not mistake one for another.**
