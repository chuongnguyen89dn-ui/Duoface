# QA132 BKS parity review vs original OmniCar, DuoNavi 1.0.4 and Native12 (2026-10-30)

## Answer: similar core mechanism, NOT exact original parity
The user asks whether the already-signed/published DuoFace QA132 follows the actual original reference DEBs. This is a source comparison, not a claim of iPhone-X on-car functional equivalence.

| Dimension | Verified original signed reference | Independent DuoFace QA132 source | Assessment |
|---|---|---|---|
| BKS symbol | OmniCar AppBridge resolves `BKSDisplayServicesSetScreenBlanked` by `dlsym`; installs `MSHookFunction` | `DFTouchOwnerProbe.m`: `dlsym`, optional `MSHookFunction`, fallback direct BKS | Same API and potential hook method; not guaranteed same installed runtime hook |
| Original blank forwards first | OmniCar intercepted BKS blank(1), if `ABHost.panes.count > 0`, calls saved original BKS(1) | QA132 `DFOriginalScreenBlank132` calls `original(blanked)` first, then checks `blanked==1` | Same ordered logic **when MSHookFunction hook actually exists** |
| Conditional pane ownership | OmniCar checks `+[ABHost shared] -count` from actual `panes` collection | QA132 checks live DuoFace UUID/heartbeat, CarPlay external display, current Chrome, `stateSnapshot.RunningScenes >= 1`, and lock-phase `protectedDataAvailable=false` | Analogous but NOT equivalent predicates; different architecture |
| Delayed unblank | OmniCar exactly **1.0 second** via `dispatch_after` on main queue, then saved original BKS(0) | QA132 **0.8 second** on main queue, then BKS(0) if ownership still valid | Same ordering, **different timing** |
| DuoNavi 1.0.4 | Distinct original conditional BKS(1/0), **0.5 / 0.3 / 0.8 second** timers with callbacks inspecting `isUIAppBridging` | QA132 uses 0.8s only, no `isUIAppBridging` callback branch | Same concept, NOT same original controller strategy |
| Native12 Dashboard | `CBDashboardSettings.screenBlankEnabled = true` constructor default (real ARM64 byte+9); conditional BKS(1/0) | QA132 has no equivalent persisted `screenBlankEnabled` setting | NOT complete Native12 settings parity |
| Injection context | OmniCar `OmniCarAppBridge.dylib` has real intercept; report doesn't establish that its loaded image is in same process as QA132 | QA132 `DFTouchOwnerProbe.plist` only filters `SpringBoard` | Exact cross-process coverage UNVERIFIED |
| No MSHookFunction fallback | Original OmniCar proof specifically intercepts original BKS(1) | QA132 uses direct guarded BKS(0) in owner watchdog when hook provider not exposed | **Material deviation**: this fallback is **not** original-first blank→unblank interception |
| Exit/teardown | OmniCar exact 1s block does not by itself prove disconnect cleanup; DuoNavi native bridge has separate state machine | QA132 cancels delayed work by serial/generation/session, and optionally reblanks on Home/disconnect | QA132 independent safety additions; not vendor-parity evidence |
