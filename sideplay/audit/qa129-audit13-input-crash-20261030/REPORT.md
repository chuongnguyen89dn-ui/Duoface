## Reproducible observations from Audit13 (read-only)
The export has 18,507 lines. `DuoFaceDeepTrace.log.previous`: 7,077 lines; UTC interval 2026-10-30 03:15:40.519–08:43:45.713, always QA90. `DuoFaceDeepTrace.log`: 96 lines; UTC 08:43:45.726–08:43:50.804, QA90. DeepTrace contains **130 `event=scene-frame-readback` observations**, split GOFA **54**, YouTube **67**, Facebook **9**. All 130 reported `same=0` at that specific measurement point (0 `same=1`).

**Do not call this proof of permanently wrong tap geometry.** In source `DFSceneHost.m`, `scene-frame-readback` is executed **before** the native scene-settings transaction, and the next before-write readback can reflect the previous target. Example: at UTC 07:25:49 (14:25:49 ICT), YouTube `actual={{0,0},{793,720}}`, `target={{0,0},{1190,720}}`, `same=0`; the code then requests native scene settings and records a commit. There is **no per-gesture, post-commit confirmation of hit-region-to-remote-scene pixel mapping** in this audit. Thus scene sizing remains a testable hypothesis, not a proved root cause.

The timestamped QA90 DeepTrace includes logo-control `raw-began`/`raw-ended`, Chrome divider commands and CPWindow session ACKs, which prove that **some first-party CarPlay UI controls receive discrete touch events**. It has **no `qa120-pane-tap` or `pane116-*` record** in the timestamped sections; the non-timestamped SceneHost section contains **one historical** `pane116-sendEvent`. Absence of these messages **cannot** prove that the YouTube app never received a tap: the existing diagnostics do not instrument the remote app's UIKit `touchesEnded` / UIControl action ACK, and the time windows/rotation are incomplete. User observation remains: same coordinates can scroll but an intended Play/button action does not fire. Do not describe this as total touch loss.

## Concrete crash comparison (different signatures)
- **13:13:03 and 13:16:09**: `EXC_CRASH / SIGABRT`. Their `lastExceptionBacktrace` contains `SBAppViewController sceneHandle:didUpdateSettingsWithDiff:previousSettings:` and the first-party `DFManagedSceneObserver`. Same Apple-observer assertion *family* as earlier cases. Both images load `DFTouchOwnerProbe.dylib` UUID **`1DDB778D-CF90-3F80-82CC-4DBCB6DD30A5`** and `DFCarPlayDockOwner.dylib` UUID **`5914DDB4-8601-34FF-AB0C-D94835D6C8EB`**. **These are not the published QA129 known UUIDs**, so the IPS must not be used to claim QA129 crashes.
- **14:25:51**: **`EXC_BREAKPOINT / SIGTRAP`** (not SIGABRT). Triggered thread starts at `-[SBAppViewController sceneHandle:didUpdateSettingsWithDiff:previousSettings:]` and `DFManagedSceneObserver`, then `DFUpdateScene`; lower stack includes `_logos_method$ImmortalizerHooks$FBScene$updateSettings... ` and `SBWorkspaceKeyboardFocusController _moveKeyboardFocusDeferringEnvironmentSceneSettingFromScene:...`. Loaded `DFTouchOwnerProbe.dylib` UUID **`692F1E47-45C1-3672-BF34-0AE53F96ABB8`**, `DFCarPlayDockOwner.dylib` UUID **`70C94BDC-ADDE-3E02-8FBE-45BEE2350960`**; Audit13 timestamped runtime **QA90** for PID 84349. This is evidence that a *different* original SpringBoard trap path passed through the DuoFace observer and scene-update hook; the presence of `ImmortalizerHooks` in the stack **does not identify it as the initiating fault**. No full text for a matching NSException reason in this SIGTRAP IPS.
- At 14:25:21–14:25:25 ICT, QA90 logs `owned-manual-observer-consumed` for two scene controllers. At about 14:25:47–14:25:49, the Chrome logo input/FocusLeft command led to a YouTube remote geometry update, and at **14:25:51** the SpringBoard process crashed; later a new SpringBoard PID appears. This chronology is **consistent with** an input/scene state transition around the crash, but not proof that FocusLeft or the app authored the invalid update.

## Decision
**Do not release a new tap/foreground/Zoom patch solely from this export.** QA37 and QA90 both physically fail user-visible tap/Play; 14:25 SIGTRAP and 13:13/13:16 SIGABRT have different exception signatures; old traces cannot establish QA129 runtime status. Narrow the next gate to:
1. Verify Sileo-installed QA129 version and *loaded dylib* UUID (`DFTouchOwnerProbe` expected `94908239-ADB0-331C-8182-5A01F2FEBAFE`, Dock expected `4BDFD10F-D309-34B3-98F7-5704B1502176` from run 41033637570).
2. Obtain a same-session **successful swipe** and **failed Play tap**, with timestamp/pane/Y-position while iPhone awake and locked. Correlate a read-only event **Began → Ended/Cancelled → hitTest / accepted UIWindow → remote app control-action / scene foreground**. Existing passive pane log has Began only; do not replay/synthesize touch or add an interception overlay.
3. Correlate a fresh QA129 crash with first-party pre-Apple-forward breadcrumbs, native scene/generation, `FBScene.updateSettings` incoming background/foreground and original observer; preserve Apple delivery for unrelated scenes. Do not guess blame from another tweak's appearance on a stack.
4. Preserve orientation QA90, divider QA92, native Dock QA120 and independent original-free code; after exact evidence, implement one minimal guarded change, macOS signed CI + immutable archive, publish via Sileo and verify parked-car hardware. No current test proves Play/Zoom repaired.

No source, Sileo publisher or original vendor DEB was modified in this read-only investigation.
