# 2026-10-30 — iOS 16 Home icon integration: original DuoFace gaps vs corroborated working third-party architecture

## Problem and corrected status
The user's requirement is **iPhone DuoFace Settings → enable an installed app → that exact app appears as a genuine, tappable icon on Apple's CarPlay Home**, in addition to optionally being chosen into a DuoFace split pane. QA133/QA134's `DFCarPlaySelectedAppCatalog.h` and `DFAppPickerVC.m` only filter the **DuoFace in-app picker**; the current signed build does **NOT** register third-party apps into native CarPlay Home. A selected-app picker is not a Home icon publisher. The user rightly challenges why this remains unimplemented.

Prior `REPORT.md` stated the actual iOS16 Dashboard gate/launch caller was not identified in original OmniCar/Native12 instruction archives; the original `OMCAppBridgeAppsController.storeChoices` only confirms preference keys `appBridgeApps`, `homeScreenHiddenApps`, `homeScreenShownApps`, and original `SCPCarSplit.publishCarPlayApps` refers to a split-app inventory, NOT Home membership. **Those negative claims about the original disassembly remain true, but a separate publicly documented reference now identifies a plausible concrete iOS16 gate.**

## Newly verified public research, no code copied or vendor package embedded
Public source `pavunato/carsurf` `main`, README SHA `f06e1d7c6558e918e0cbcbb160b78ca01a63c360`; `docs/ios18-runtime-carplay-admission.md`; `sbtweak/CSSceneManifestSpoof.m` SHA `c5c94ebc286a1286c1e5e0535be1194f4fcb6653`; `sbtweak/CSAppList.m` SHA `9de45f39a292fb776be969d3db195b8f9803f79b`; `sbtweak/CSCarLaunch.m` SHA `b441933ba2e9a2f6886eca5cfa1686619a95097f`; `docs/carplay-live-icon-sync.md`. This reference reports **actual iPhone X 16.7.12 RootHide testing**, not a verified DuoFace iPhone X 16.7.16 palera1n session. These are independently inspectable public sources, NOT a license to copy their method bodies or binaries; no code was copied into DuoFace.

Observed architecture from that source:
1. iOS **15–17** uses **LaunchServices** for app admission; not the iOS18+ CarKit declaration/policy path. In CarPlay UI, DashBoard `+[DashBoard _newApplicationLibrary]` / related inclusion filtering consult typed `LSBundleProxy entitlementValueForKey:ofClass:valuesOfClass:` (also two-param wrapper). A user-approved app absent genuine CarPlay entitlement needs a narrowly bounded *in-memory* admission answer; touching the app's on-disk entitlement, bundle or signature is not required.
2. SpringBoard has a distinct app-info gate: `FBSApplicationInfo entitlementValuesForKeys:` returning a private `LSBundleInfoCachedValues` object, then typed getters, including `boolForKey:`. A **CarPlay-process-only** hook does not satisfy this separate gate.
3. Native CarPlay Home app inventory is a different object than the app picker: iOS16 `CARApplication` app-library APIs (example `_allInstalledApplicationsByBundleIdentifier`) include real native apps and only explicitly enabled bridged bundles. Genuine app objects and Apple native roster must be preserved.
4. Icon tap launch goes through the real CarPlay DashBoard workspace / `DBApplicationController` application identity, not our `DFAppPickerVC` tap handler, and scene role/configuration has to be compatible with a real CarPlay window. Merely creating a thumbnail or adding an unsupported bundle ID to a string array will not launch a live app.
5. Do **not** apply iOS18 CarKit path to the user's iOS16 target. The reference documents unsafe approaches: global entitlement dictionary replacement, `carkitd` hooking, late template-scene rewriting, raw icon-layout reconstruction and blind policy mutations. Their live hidden-icon service information refers primarily to iOS18.5 and is **not** proof of the 16.7.16 service ABI.

## Crosswalk to DuoFace: what is already present vs actually missing
- `DFNativeHostRootController.m` writes the user-chosen `DFEnabledAppsPath` `EnabledBundleIDs`, while `DFCarPlaySelectedAppCatalog.h` validates installed+enabled. This is **permission and picker state**, not native Home registration.
- Existing signed receiver `DFCarPlayDockOwner.m` runs in `CarPlay` and associated processes; `DFTouchOwnerProbe.m` in `SpringBoard`. They already provide two separate injection targets; there is **no Home admission code** linked into either. Avoid changing their existing Dock/touch ownership or Home teardown.
- Historical isolated `sideplay/firstparty-carplay-admission/DFFirstPartyAdmission.m` tested CarPlay-only typed `LSBundleProxy` getters gated to only **DuoFace's own host**. `DFFirstPartySpringBoard.m` explored matching FBS cached-value gate, but remains an isolated candidate, not the signed app-roster feature. User device once observed 'hook armed, no CarPlay icon' for a CarPlay-only variant. It is invalid to infer the iOS16 entire mechanism doesn't exist from that partial, first-party-only attempt.
- **Missing actual runnable bridge:** independently designed, ABI-validated and reversible two-process app admission; exact user-chosen *installed* IDs only; app scene role/launch compatibility; native catalog selective membership with OS originals preserved; dynamic refresh and disconnect; on-device real icon/tap/scene verification. The current signed QA134 remains GOFA owner fix ONLY.
- Native Apple Home is per-vehicle; settings-based hidden/shown policy is not the same as app admission. Do not overwrite native per-vehicle icon layout or produce fake CarPlay Home tiles.
