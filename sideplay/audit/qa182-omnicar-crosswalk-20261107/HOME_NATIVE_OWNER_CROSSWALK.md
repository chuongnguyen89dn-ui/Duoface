## D. First-party exact root cause and scoped repair design (NOT IMPLEMENTED)
1. `DFCarPlayOwnerObserver.h:DFOwnerObserveNative` is a single writer (CarPlay process), bound only to unique `com.duoface.native.scenehost` `candidate` controller/scene; when Maps foregrounds and DuoFace backgrounds, it writes `Active=0`.
2. `DFCarPlayOwnerLease.h:DFOwnerEvidenceMatches` hard-requires `Bundle==com.duoface.native.scenehost`, exact old `HostSceneID`, `HomeHookReady`, `Active`, age <=1.25s. `DFOwnerAcceptRecords` requires this exact old attestation if `HostBackground` is true.
3. `DFTouchOwnerProbe.m:DFWatchdog` polls each 0.5s, calls `DFOwnerAcceptPulse`, then `DFStopProbe` and `DFNative12Chrome.stop` on denial. `DFNative12Chrome.m:stop` revokes Maps assignment, tears down other pane. The predicate is wrong for the **legitimate explicit Maps native handoff**, while correct for arbitrary background/disconnect.
4. `DF182NativeMaps.m:-owns:` already verifies live exact Maps controller + FBScene + assignment UUID + window + containment. Yet **this positive proof is never consumed by the SpringBoard lease**. A saved assignment alone is not live attestation.
5. Separate source transaction defects: `DFNative12Chrome.m:assignNativeMaps182:` writes assignment and drops prior selected scene too early; `layoutControls` hides SB physical slot from assignment alone (`nativeReserved`) even before verified native placement; `DF182NativeMaps.m:-fail:/-restore:` may return with `!placed` without revoking assignment or restoring hidden/previous pane. Frame PASS after teardown should become invalid.
