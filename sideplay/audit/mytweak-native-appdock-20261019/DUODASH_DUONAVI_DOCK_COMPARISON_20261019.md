# Comparison: DuoDash 1.1.3 / DuoNavi 1.0.4 / MyTweak Dock (2026-10-19)

Read-only review. No source, package or Sileo update. User requires native Apple AppDock/Home alongside two independently hosted iPhone apps.

Apple official CarPlay requires category-specific managed entitlements. There is no general official entitlement for arbitrary iPhone mirroring: https://developer.apple.com/documentation/carplay/requesting-carplay-entitlements . Public reference https://github.com/pavunato/carsurf documents a distinct jailbreak runtime technique for app scene admission; do not attribute its exact methods to either closed-source DuoDash or DuoNavi.

DuoDash: vendor https://sensetechlab.com/duodash/features/ says an icon launches DualApps from CarPlay Home and App Bridge adds selected iPhone apps to the CarPlay Home icon grid; vendor screenshot shows native left sidebar alongside two panels. Existing repository static crosswalk `audit/duodash-1.1.3/DUODASH_APPBRIDGE_VISUALTEST12_CROSSWALK_20261017.json` describes SpringBoard request and host layers (`CNABSpringBoardObserver`, `DDz2`), CarPlay UI state (`CNABUIApp`, `DDz1 showLayoutPanes:natives:bids:`), and injection into CarPlayApp. Specific Dock frame/visibility algorithm NOT yet verified in binary.

DuoNavi original 1.0.4: audited original ARM64 methods in `audit/duonavi-original104-ui/ORIGINAL104_UI_CALLCHAINS.json` at branch `feature/visual12-duodash-recovery`. `CBWindow.createWindows` 0xb173c reads `carPlayWindowScene`, `carPlayUIScreen`, `carPlayCADisplay`; may create from UIWindowScene or FBSDisplayConfiguration. `carPlayContentInsets` 0xb1370 reads optional text geometry or root window `safeAreaInsets`; `carPlayUsableBounds` 0xb15cc computes inset area; `resizeWindows` 0xb24ac and hosted scene layout use that area. Thus DuoNavi also has an independently built window path, correcting our previous unsupported assertion that a custom window *necessarily* removes native Dock. This confirms an additional content-insets model, NOT that insets alone ensure system Dock displays.

Related Native12 (DIFFERENT executable) metadata `audit/payload-migration/NATIVE12_CONNECTION_FULL_OWNERS_READONLY.json` has `CBBridgeManagerDashboard` selectors `prepareHomeScreenForBridge:`, `handleDockIconTap:`, `setAppDockActiveBundleID:`, `setHomeButtonInApp:`, `getDockDimension`, `getDockWidth`, `getDockEdge`. It also has `CBBridgeManager receivedDockTapNotification:`. These are static metadata, not proven runtime path in DuoNavi original.

Our MyTweak uses external `UIRootSceneWindow` with full frame and no earlier `carPlayWindowScene/safeAreaInsets/carPlayUsableBounds` pipeline or Home/Dock event contract. Device logs show fallback full frame before Zoom and no valid native Dock record; user confirms dock1 not improved. Root of Dock absence not yet isolated between window z-order, Dashboard routing or Dock visibility. Fix requires measuring the correct CarPlay scene/usable area AND coordinated Home/Dock behavior, while preserving the working split/scene host. Never paint a fake Dock, import vendor license, or deploy speculative binary.
