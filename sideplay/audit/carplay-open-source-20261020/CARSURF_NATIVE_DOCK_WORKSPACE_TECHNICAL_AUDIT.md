# CarSurf native CarPlay Dock / scene ownership — source audit (2026-10-20)

## Required behavior / non-negotiable
User correction: Native system CarPlay Dock must be visible *automatically and continuously* in NORMAL mode, as it is for an ordinary CarPlay Dashboard application. **No explicit bar-show command, no positioning DBStatusBarWindow, no fake/custom Dock, no special 45-second opt-in.** Fullscreen is only intentional user action; restoring NORMAL returns to ordinary native Dashboard layout. Preserve real app touch, dual-pane split, ratio/Swap/Zoom, safe recovery versions. Project repo `chuongnguyen89dn-ui/Duoface`, current proven public QA6 `0.0.6~dockcrop1`.

## Direct verdict
**CarSurf source architecture does NOT draw, summon, position, or hide the system Dock to make its app appear.** It adds chosen app(s) to the native DashBoard roster and sends native scene/window role requests via CarPlay's own app/scene lifecycle. Its content respects `UIWindowScene.coordinateSpace.bounds` and `UIWindow.safeAreaInsets`. This *strongly supports* natural CarPlay UI chrome persistence **by design**, rather than a manual Dock visibility command. However no independent device screenshot/measurement of native Dock persistence on user's iPhone X/DiPlay was obtained; source audit ≠ device-proven default Dock.

NO Dock window creation.
2. `https://github.com/pavunato/carsurf/blob/main/sbtweak/CSSceneManifestSpoof.m` (blob `c5c94ebc286a1286c1e5e0535be1194f4fcb6653`) — iOS 16/17: selectively modifies *runtime* LaunchServices entitlement/scene-role answers for enabled bundles; marks `CARCapableApp`/`SBStarkCapable`, adds CarPlay-native window scene role `UIWindowSceneSessionRoleCarPlay`, `UIApplicationSupportsMultipleScenes=true`; where relevant suppresses template entitlements/roles so the normal phone app scene is used instead of `CPTemplateApplicationScene`. It does NOT edit installed app files and does NOT manipulate actual Dock frame. This is private API hooking and **not Apple-approved app entitlement issuance**.
3. `https://github.com/pavunato/carsurf/blob/main/sbtweak/CSCarLaunch.m` (blob `b441933ba2e9a2f6886eca5cfa1686619a95097f`), `CSNoteWorkspace` only captures `DBWorkspace` owned by `DBDashboardWorkspaceOwner` (not instrument cluster); `CSCarLaunch` uses `DBApplicationController.sharedInstance`, `DBMutableWorkspaceStateChangeRequest.activateApplication:`, `DBWorkspace.requestStateChange:`. **Important distinction**: a `carsurf-launch` command is a **testing shortcut** sending a notification into that native workspace; the file documents this as reproducing the SAME flow as a human tapping an app icon on Dashboard, NOT a requirement to show Dock or normal app startup. Ordinary user launches are through the native Dashboard app icon.
4. `https://github.com/pavunato/carsurf/blob/main/apptweak/CSSceneBridge.m` (blob `e727b34484af37f5fa68121e96479b04b6396294`), `cs_initWithNameSessionRole`, `cs_sessionRole`: converts incoming CarPlay-role session to regular app `UIWindowSceneSessionRoleApplication` *before UIKit constructs the scene*, letting app's scene delegate create a real interactive window. `CSCarSceneConnected` is invoked on `UISceneDidActivateNotification`, after root window exists; disconnect prunes session ID so reconnect is fresh. NOT a snapshot view. `CSCarViewportForWindow`: reset window transform and full logical scene frame `window.frame=scene.coordinateSpace.bounds` BEFORE querying native `window.safeAreaInsets` to avoid accumulating insets; computes rect from ALL four native insets, logs currentMode/native bounds. `CSApplyScaleToCarScene`: positions actual window within derived area. No hard-coded 45pt or call to show native bar.
5. `https://github.com/pavunato/carsurf/blob/main/apptweak/CSMirror.m` (blob `9cd97386b92086eedb116c6410d988837abfac93`) — fallback for legacy apps without scene manifest: `CSConfigureTransplantWindow` puts real root controller/window inside a CarPlay-owned scene viewport, rather than screenshot replay. Their own README admits one root VC cannot be duplicated to phone+car simultaneously.
6. `https://github.com/pavunato/carsurf/blob/main/apptweak/CSApp.m` (blob `ed20534f5fe397289ebd16c8337e164ca7453ea2`) — installs app-side scene bridge for enabled apps and excludes SpringBoard/CarPlay host from app-side injection. Logs show actual UIWindowScene activation/processing.

**No direct Dock show/hide or `DBStatusBarWindow` frame-setting occurs in these inspected registration, launch and scene bridge paths.** This is a bounded source inspection, not a claim no other unpublished component or system behavior exists. GitHub repository metadata returned license=null, tree has no LICENSE: public-viewable source is **not freely copyable into independent DuoFace** without permission.

## Counter-evidence: actual DuoFace QA6 is NOT natural Dock
Branch `feature/duoface-dock-crop-livewindow-20261020`:
- `sideplay/mytweak-independent-v1a/MTBridgeCoordinator.m`: SpringBoard creates full-display foreign `UIRootSceneWindow` with `FBSDisplayConfiguration`; not native Dashboard-owned app scene.
- `sideplay/mytweak-native-bridgeqa/DFNativeSidebarTrial.m` (blob `2ed81197c3fa9a12a4683cf173c8c0efeeea40ef`): explicitly looks for CarPlay `DBStatusBarWindow` + `DBRootStatusBarViewController` that starts *off-screen* at x=-width, then sets `candidate.frame=destination` to pull it into view. `NSDate.date.timeIntervalSince1970-self.beganAt>45` moves it back to original system window position. **This is a forced Dock/system-sidebar manipulation; must NOT be the final implementation.**
- `sideplay/mytweak-native-bridgeqa/DFCPNativeBridgeQA.m` (blob `4c10c47220b729641e502dda120d01ae8c6aa8c9`): separate `tickNativeDashboardSourceYield:` changes *SpringBoard foreign source UIWindow frame* on CarPlay ACK, with `yieldSince>45` resetting it to full display and exhausting same-session trial. **Two separate 45s revocations can produce alternating apparent Dock/full-screen states.** Need user runtime log to correlate exact observed transitions, but mechanism exists from source.
- `sideplay/mytweak-independent-v1a/prototype/MTCPDashboardOwner.m` attaches another receiver only inside a measured native content rect; QA5/QA6 also perform `drawViewHierarchyInRect` raster/pointer-to-menu fallback; this is not the CarSurf full live scene path.

## Architecture decision (research completed; not yet implemented)
**Do not 'fix' native Dock using any system statusbar frame/hidden property, `DDFindDock`, custom Dock, 45pt crop constant, repeated `windowLevel` changes, or timed leases.** At NORMAL startup:
1. Build/test first-party **DuoFace CarPlay app admission/scene** path on isolated branch: selectively surface only the independent DuoFace host as an application to the native Dashboard / CarPlay workspace (or a supported app category/scene when actually authorized). Let the CarPlay-process `DBWorkspace` and ordinary app icon activation own foreground state and create an app-associated interactive `UIWindowScene`. Treat third-party CarSurf as behavior/API **research only** (no source transplantation; license absent). Never claim adding Info.plist alone grants an entitlement.
2. Wait for the actual CarPlay UIWindowScene lifecycle and `UISceneDidActivateNotification` before attaching our owner-controlled UI. Measure **native** `scene.coordinateSpace.bounds` and `safeAreaInsets` once from full bounds before applying layout; update on real geometry changes and scene reconnect, not timers. If not admitted, *fail closed*, keep Apple UI untouched and emit diagnostic log to iPhone QA app.
3. First device-gate: Sileo-installed isolated DuoFace app icon appears among CarPlay apps without manual Dock trial; tapping it leaves **native Dock/Home visible** for >2 minutes without third opt-in or bar movement, real Home works, one phone app interactive with gestures; disconnect/reconnect stable. Do not assume iOS16 methods/hooks identical on each jailbreak, rootless crash history includes SpringBoard boot loops.
4. Only after gate 3: integrate **existing V1BC split** (two iPhone app scene hosts) without using QA5 screenshot mirroring. CarSurf's native Dashboard normally activates **one app at a time**; it does not natively demonstrate two arbitrary app scenes inside one split view. This is a distinct challenging component; avoid promising split works merely because native Dock works.
5. Preserve published QA6 and recovery, Native12/HUD8/QA11; new Theos CI + separate opt-in Sileo package only when guarded candidate compiles and compatibility verified. Leave old trial available solely for recovery, not normal operation.
