## Gate 0: authoritative ON/OFF per-record stock-setting readback — mandatory before ABI/event comparison (new user instruction)
**Root cause verified in QA182 source**: `sideplay/duoface-native-scene-host/DF182NativeMapAssignment.h:DF182Log` literally embeds `stock-settings=unknown` in **every** `qa182-b1` trace line; `sideplay/native-carplay-scene-v1/DF182NativeMaps.m:-summary:` writes `r[@"StockSettings"]=@"unknown"` to result plist. Therefore Audit11 was *structurally unable to distinguish ON vs OFF*, regardless of its extensive scene/callback telemetry. Do NOT solve this by merely adding fields to the logger while leaving its value unknown.

**Measurement prerequisites (P0-0, before any state-changing fix):**
1. **Prove one concrete actual iOS16.7.16 CarPlay-Customize authority** for Google Maps under the CURRENT paired car profile. Identify exact owning process, runtime class/selector or persistent settings domain/key plus its data type, how it corresponds to the current vehicle, runtime permission to read, and whether it reports original iOS Customize **ON/visible vs OFF/hidden**. Do not guess a plist/key from another iOS version, do not equate app-native `carPlayDeclaration` with Customize visibility, do not use DuoFace `EnabledBundleIDs`, picker selection, FBS membership or native Home icon presence as a fabricated settings oracle. No authoritative source is verified **yet**; its existence/mapping is a blocker to close in this first measurement step.
2. **Bidirectional calibration on the same parked device**: read the candidate source while ON → change only Google Maps Customize to OFF → read again → restore ON → read again (optionally OFF again for acceptance). Correlate the *source's raw result*, observed UI state (screenshots or operator audit, explicitly marked as external corroboration), live paired vehicle context and timestamps. Require exact ON/OFF/ON transitions with fresh readback in the correct car profile; distinguish persisted setting from cached UI/notification and check observation after reconnect if required. ## Evaluation: APPROVE with 3 mandatory amendments
1. **Source of truth across processes, not shared object:** CarPlay-process presentation owner is the authoritative writer of actual native membership; SpringBoard watchdog only validates a versioned, atomic, fresh, session/AssignmentID-scoped live attestation and revoke signal. Assignment intent or launch ACK cannot self-certify presentation. Exact controller/FBScene/CarPlay role/external window, physical pane and post-presentation frame/visibility must be verified. Home/unassign/scene destruction/disconnect revokes. Keep existing normal DuoFace-nativehost path and independent Home safety.
2. **Do not misread 'no reparent to Dashboard root' as no legitimate UIKit containment:** QA182 put a UIView pane under `DBDashboardRootViewController.root.view` (DF182NativeMaps.m lines 322–334) without intercepting Dashboard's fullscreen presentation; vehicle visually showed Maps in the stock Dashboard. Need an ABI-verified hook of actual **presentation decision** and independent one-pane composition owner (likely in CarPlay process), with correct UIWindow z-order/clip/hit region. The rightful controller could still be a descendant of Dashboard's view hierarchy when that root hosts the first-party split presenter; **the forbidden pattern is treating a blind addSubview/reparent as ownership**. Never steal/clone CPWindow or phone-host Maps as a surrogate for native CarPlay.
3. **Preflight OFF in stage 1, not only final gate:** On this phone, “OFF in CarPlay Customize” may mean Home icon hidden or stronger CarPlay capability/eligibility removed. The only existing QA182 artifact logs `stock-settings=unknown` in all measured events; cannot infer. Run tightly tagged **ON control → OFF case** with screenshots of user configuration and synchronized time/AssignmentID; check original `carPlayDeclaration`, native Dashboard/FBS membership, DBWorkspace launch eligibility, real DBApplicationSceneViewController+FBScene creation, scene role, surface and ability to receive input. If OFF yields genuine native scene, same verified presenter transaction should work without re-enabling stock Home icon. If OFF suppresses required native scene altogether, report **hard feasibility blocker** and research explicit native eligibility path; do NOT silently claim success, spoof native declaration, force Home ON, or fall back to iPhone/main-display Maps.

## Transaction invariants for future design (NOT IMPLEMENTED)
- State machine: `IDLE → INTENT_RESERVED → NATIVE_PRESENTATION_OBSERVED → PANE_MEMBERSHIP_VERIFIED → COMMITTED`, otherwise `ROLLED_BACK` or `REVOKED`. Only COMMITTED can hide previous pane or renew alternate-background owner. All callbacks carry and validate Session UUID, AssignmentID UUID, physical slot, scene identity, monotonic generation, live CarPlay window and timestamp.
- At the presentation gate, identify genuine `com.google.Maps` native VC and issue precise adopt/owner transaction, not screenshot cropping or Dashboard-root overlay. Verify native scene frame, scoped safe-area insets (ABI first), root geometry, z-order, native pixels/touch. Native Home action and foreign-scene destroys cannot silently resurrect stale placement; callback completion is exactly-once with original fallback for non-owned controllers.
- The SpringBoard heartbeat watchdog must keep functioning for stale, Home, unplug, replaced assignment, invalid scene and normal host path. Permit alternate native Maps owner only after a verified COMMITTED receipt from single writer. On failure restore old view/scene/phone-pane visibility and stock Home/Dock state, report sustained FAIL even if local frame previously PASS.
- Existing H1/QA180 touch, keyboard, GOFA/YouTube, Dock, zoom, app selection, original Home app grid and current Darwin notification remain protected. Never copy original OmniCar/DuoNavi bodies or license policy.
