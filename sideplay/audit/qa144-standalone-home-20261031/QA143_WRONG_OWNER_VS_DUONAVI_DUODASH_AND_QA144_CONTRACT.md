# QA144 — explicit user correction: CarPlay Home third-party app must NOT enter DuoFace split UI

## Latest user requirement (supersedes QA143)
User: "Ko đúng. Khi mở app ngoài carplay thì nó mở ra giao diện dùuoace chế độ chia màn hình. Bạn ko làm theo các deb khác dfc?"

**Interpretation confirmed by the implementation error**: Selecting a user-enabled third-party app **from the actual CarPlay Home outside DuoFace** must open the **selected app directly**, in a dedicated full CarPlay content scene **without launching DuoFace's split screen, app picker, logo, windows or restore queue**. Within DuoFace itself, its existing split and 1/2/3/4 physical-panes continue untouched. This corrects the QA143 acceptance criterion even if a phone happens to have produced some app frames. Home/Back returns to Apple CarPlay Home and native Dock. Do not confuse a full-screen app as a pane maximized under a running DuoFace split mode.

## Root cause — verified from exact QA143 source, not inferred from user device
QA143 `sideplay/duoface-native-scene-host/DFHomeLaunch143.m` explicitly searches for a real `com.duoface.native.scenehost` Home icon and substitutes that icon in the ORIGINAL `DBDashboardHomeViewController iconManager:launchIconForIconView:` callback. It then writes an app intent. `DFNativeHostAppDelegate.m` legitimately activates DuoFace CPTemplate. SpringBoard `DFTouchOwnerProbe.m` calls `DFHome143ConsumeRequest(sChrome,sSession)` after `[sChrome start]`. `DFHomeSceneBridge143.m` uses `[self setSelectedSlot:0]` then calls `[self appPicker:picker didSelectBundleID:bundle displayName:bundle]`. That method is the **split-pane** scene factory in `DFNative12Chrome.m`. Therefore QA143 is **wired by design** to enter the DuoFace split UI and does **not** meet this user requirement. This is an actual source implementation mistake, independently of whether an external app opens after the pane.

## Correct ownership boundary for independent DuoFace
```
CarPlay Home: user taps selected ordinary app icon
  -> native DB Home callback, identified exact ABI in Log21
  -> selected-only first-party StandaloneLaunch broker
  -> genuinely independent, fresh single-app scene owner in SpringBoard
  -> display app host surface directly on verified CarPlay content display
     (normal native Dock kept; no DuoFace Chrome, no picker, no split windows)
  -> scene ready proof with correct bundle / validated PID, real input
  -> Home/Back/disconnect revokes standalone owner / releases scene
```
- **Do NOT activate `com.duoface.native.scenehost` or substitute its icon**. Do NOT call `DFNative12Chrome.start`, `appPicker:didSelectBundleID:`, `setSelectedSlot:0` for a Home-origin external app. Keep all those available **only** when user explicitly enters DuoFace.
- A standalone host can reuse only the independent **primitive** `DFSceneHost hostViewForBundleID:error:` in SpringBoard, attached to a **separate dedicated one-app full CarPlay content owner**, not to the split chrome. This is a design constraint, not proof the needed one-app host/window is implemented.
- Correct Home selected callback must NOT silently forward a substituted DuoFace icon. For native/unselected/unsupported/unknown, original callback exactly once. For opt-in third-party, selected-only broker must have a successful bounded launch admission (fresh request ID, valid host, home/connection owner) before consuming event; fail-open on missing owner, unknown ABI or failed IPC. No broad entitlement hook; QA138 had historical FrontBoard recursion crashes.
- Dedicated CarPlay display content rect must be measured from original system Dock/root (previous QA120 owner evidence) and must not create fake `CPWindow` or mask Apple Dock. No automatic startup from iPhone background; no stale lease. Full CarPlay *content* does not mean hiding system Dock.
- The real `DFSceneHost` has asynchronous `sceneReady` / `sceneFailed`, so callback acceptance is not evidence of video/input. Need lifecycle and user hardware test on parked system, including real Home/Back, lock, GOFA and YouTube, before claiming success.
