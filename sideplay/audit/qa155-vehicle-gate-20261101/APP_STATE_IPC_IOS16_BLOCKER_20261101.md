# iOS16 app-process state relay — verified transport blocker (2026-11-01)

## Objective
Continue first-party independent DuoFace CarPlay native Home→Dock→scene→app-process integration, not a VLC-only or log-only QA. User explicitly rejects repeated DEBs before underlying native path works.

## Repository/runtime evidence
- Actual repo `chuongnguyen89dn-ui/Duoface`, branch `feature/duoface-qa146-native-home-exit-20261031`, inspected at source tree of `32f3d96f37691ba03d87ddfc419a0678aade4023`.
- `sideplay/duoface-native-scene-host/DF154AppStateProtocol.h:47-62`: sender `DF154Post` and `DF155PostAck` depend on `DF154Center()` based on `NSClassFromString(@"NSDistributedNotificationCenter")`; nil center means a silent no-op for both directions. Source invokes center selector `addObserver:selector:name:object:` (four-argument), whereas documented distributed notification registration uses the `...suspensionBehavior:` API. No iOS availability guard or working fallback.
- `sideplay/duoface-native-scene-host/DF154GeneralAppStateRelay.m`: app only registers listener when `DF154Center()` succeeds, otherwise logs `transport-unavailable; no UIKit changes` and returns. The app-side `lease-accepted`, `scene-matched`, `window-adjusted`, and ACK cannot occur in this path.
- Apple NSDistributedNotificationCenter documentation describes a process-wide computer/macOS distribution center. Microsoft .NET native framework mapping lists macOS and MacCatalyst, not iOS. This is strong platform-level evidence the current transport is not available on native iOS16; **direct iPhone runtime Class lookup has not been performed**, so do not assert actual Class runtime verification.
- Log24 (`sideplay/log/DuoFaceAudit 24.txt`, blob `1f21a2095bdcd735e3c24fa7df0ef122d58cb629`) had **zero `qa155-app-side-ack`**; this is consistent with unusable transport but insufficient alone to prove the class lookup result, because that log has zero VLC/Safari requests in the latest window.
- `sideplay/duoface-native-scene-host/DFAppViewportRelay.m` and `DFAppViewportProtocol.h` already use iOS Darwin `notify_register_dispatch` / `notify_get_state` with a validated short lease/width-height payload, and exclude phone-main UIKit scene. This is an **in-repository implementation precedent** to build an iOS-compatible transport, not proof it is wired into current signed package: current `build.sh` compiles `DF154GeneralAppStateRelay.m`, not `DFAppViewportRelay.m`.
- Original earlier native member/manager/Dock adjustments have been committed and private signed; latest successful build before this audit: run `41258321320`, source `d4b2ba2489ec2acc33881c05b9c507bc895a5a5e`. No hardware validation or Sileo publication.

## Concrete next engineering action
Replace the macOS-only `DF154Center` with a real **native iOS 16 per-scene, selected-app scoped cross-process state transport**, initially using proven Darwin notify primitives `notify_register_dispatch/notify_set_state/notify_get_state/notify_post` or an available authenticated first-party IPC. Preserve exact scene identity, per-request owner/generation and consent checks; do not convert identity-scoped messages into a global width-only broadcast. Require request-bound ACK from the selected app and restore on revoke; avoid modifying unrelated phone scene, YouTube, GOFA, CarPlay Home or native Dock. Add tests that reject `NSDistributedNotificationCenter` in the iOS app-side transport, exercise active/revoke/expired/mismatch, confirm original checks. Only then build one signed DEB via existing private workflow, archive SHA in DuoFace repo, deliver under **unique version through existing Sileo root** (never overwrite equal-version QA155 or create /qa155/ beta source) when safe; actual CarPlay acceptance remains dependent on iPhone/vehicle test. This is a verified design blocker and next action, **NOT a claim code fix was made**.
