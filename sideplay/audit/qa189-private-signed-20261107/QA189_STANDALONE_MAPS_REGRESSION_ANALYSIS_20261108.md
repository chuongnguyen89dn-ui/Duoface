## Source-level causal chain (VERIFIED code, actual saved-state values NOT yet measured)
1. In `sideplay/duoface-native-scene-host/DFSlotWorkspacePolicy.h`, workspace defaults `RestoreOnReconnect=@YES` (line 41), persists four `PhysicalBundles`, and `DFRestorablePhysicalBundles` (126-140) restores saved installed+allowlisted bundles when enabled. QA189 does not make a special default-off exception for native Maps.
2. `sideplay/duoface-native-scene-host/DFNative12Chrome.m` `start` (lines 1149-1182) finishes the logo startup then **automatically** calls `beginSavedWorkspaceRestore`. It also does so immediately on same-connection Home reentry without splash. `beginSavedWorkspaceRestore` (391-409) queues saved physical apps and `restoreNextSavedWorkspaceApp` (435-464) checks `[bundle isEqual:@"com.google.Maps"]`, then calls `assignNativeMaps182:origin:@"workspace-restore"` WITHOUT a fresh user touch. It logs `qa188-native-maps-saved-restore-request ISSUED`. This is the primary, code-proven route for automatic Maps activation **IF** Maps is saved/enabled/installed in the actual device workspace. Whether that prerequisite held in the observed session still needs log/preference readback.
3. `assignNativeMaps182:origin:` (2053-2078) creates live `DF182AssignForOrigin`, writes the same `com.google.Maps` to saved workspace (2073) and closes the picker/updates layout, but does not await a native pane `COMMITTED` or prevent Apple stock focus. It can perpetuate the saved Maps selection on the next reconnect.
4. `sideplay/native-carplay-scene-v1/DF182NativeMaps.m` `tick` (497-547) receives assignment and invokes `DF182CatalogAndLaunch`. The implementation in `sideplay/duoface-native-scene-host/DF182DashboardBridge.m` (16-39) explicitly calls `DBMutableWorkspaceStateChangeRequest.activateApplication:` and `DBWorkspace.requestStateChange:` (33-34). This is a **stock CarPlay workspace activation** of Google Maps, not an in-pane guaranteed display. It happens BEFORE a true pane membership or UIKit containment commit. Thus the source is capable of exactly the user-observed switch to standalone Maps even if all later pane gates fail.
5. `DF182NativeMaps.m` hooks `DBDashboardRootViewController.presentBaseViewController:animated:launchSource:completion:` (129-159): it calls the Apple original FIRST (131), then checks whether a fully attached native `DBApplicationSceneViewController` already has correct root, window, scene and owner (133-146). Actual placement into `DF186NativePaneController` happens LATER in `tick` (559-628), only after candidate and membership/visibility/geometry checks. There is no guarantee that original foreground transition is invisible to the driver.
6. On failure `DF182NativeMaps.m` `fail` (414-420) calls `restore` (383-413) and `DF182Revoke`; `DF182Revoke` in `DF182NativeMapAssignment.h` (67-76) deletes the assignment and notifies. This restores/revokes *internal UIKit containment*, but it does **NOT** issue a compensating `DBWorkspace` state-change to restore the original DuoFace foreground. Therefore a native launch/admission failure can leave system Google Maps frontmost and DuoFace split lost. This is a concrete missing rollback contract in source, although its exact runtime failure gate remains unknown.
7. `DF182NativeMaps.m` `DF182Frame` (108-125) explicitly returns the original OS frame unchanged even when it calculates target half-pane; its log says `override=DISABLED native-split-size=UNVERIFIED`. This protects against earlier scene-size corruption, but the native FBScene is still born with stock/full-screen geometry. Later `UIView` clipping alone is not proof of true native scene size/input split.

## Additional likely failure gates (not established as actual QA189 vehicle trigger)
- **Async presentation race:** `DF182Present` checks `vc.viewIfLoaded.window` and exact owner immediately *after* original presenter returns, not after a settled presentation completion. On an async transition, it can return early and lose the only matching PRESENTED event. Check `b1-present-member`, `b1-present-member-rejected`, `b1-present-identity-rejected`, then `b1-native-scene-provenance-timeout-10s-STOP` to distinguish. A prior QA185 admitted and committed before losing attestation, so do not assume same outcome now.
- **Very short two-process yield window:** `DF184NativeMapMembership.h` accepts `PRESENTED` only within 0.85s (73-78), while the CarPlay owner polls every 0.25s (`DF182NativeMaps.m:639-642`), SpringBoard reconciles after Darwin event, and native owner heartbeat uses a 0.75s timer (`DFNativeHostAppDelegate.m:270-275`). Small scheduling latency/scene lifecycle changes can consume the available window. Check `qa189-native-map-stage-changed stage=PRESENTED`, physical `WindowVisible` and `b1-presented-target-yield-expired-before-COMMITTED-STOP`; avoid asserting that 0.85s is the actual cause without timestamps.
- **Host background loss / H1 collateral damage:** `DFNativeHostAppDelegate.m:289-315` stops the CPTemplate touch owner on `sceneDidEnterBackground` if neither valid host owner nor fresh native Maps membership evidence is available. This may happen BEFORE native COMMITTED when Apple switches to standalone Maps. `DFTouchOwnerProbe.m:541-553` watchdog then stops Chrome on invalid pulse; `DFTouchOwnerProbe.m:480-511` calls `[old stop]`, ending split and potentially H1/controls. Keep Home revocation security; do not work around it with fabricated owner pulses or an immortal overlay.
- **Legacy second route:** `DFNativeMapPaneCoordinator.m:397-424` has a `autoRestoreAfterReconnectIfVerified`, but lines 310-346 only attempt to reattach an already-live native controller after exact geometry/owner verification; there is no `DBWorkspace.activateApplication` in that legacy method. This should be instrumented to prevent competing owners, but is NOT the primary automatic foreground launch identified above.

## Decision and recommended repair design (NOT IMPLEMENTED)
Priority 0 — **prevent default standalone takeover**: separate persisted native Maps choice from authorization to activate CarPlay workspace. Preserve user saved slots, but on DuoFace startup/reconnect treat a saved Maps slot as `PENDING_NATIVE`/restore intent, NEVER auto-call `assignNativeMaps182`/`DBWorkspace.activateApplication` solely from `RestoreOnReconnect`. Restore other saved non-native apps as before. Render the real DuoFace split/peer without faking Maps pixels. Require an explicit user action or strictly verified non-foreground native scene availability before initiating native Maps transaction. On startup with saved Maps, requirement: no `b1-launch-issued` and no CarPlay focus switch.
Priority 1 — **fix native scene ownership before changing foreground**: map picker request should carry session, assigned physical slot, initial active CarPlay workspace/scene identity, and a strictly bounded pending transaction. A real native presenter must be proven capable of placing the Maps scene into the designated DuoFace pane and preserving peer/Chrome **before** labeling it success. The existing `DBWorkspace.activateApplication:` is explicitly a stock full-app activation; do not treat it as an in-pane API. Investigate a system-managed non-frontmost native scene creation/presentation path using observed iOS16 ABIs, or an attach-only path when an actual native Maps CarPlay scene is already live, with no vendor code or licensing copied. Do not re-enable the earlier unsafe `sceneFrameForAppInfo` prelaunch resize without exact inverse scene-size proof.
Priority 2 — **atomic foreground compensation**: if an explicit native launch does foreground stock Maps and verified pane transaction fails, restore the *exact prelaunch system workspace owner* safely (only for matching original session/assignment, no Home user action or fresh replacement). Current `DF182Revoke` only clears internal assignment. Do not force-activate another app, globally hook Home, or cheat by drawing Maps screenshot; the return path and Home/disconnect safeguards need real on-car verification. If no supported compensating workspace operation can be proven, block that launch path instead of leaving standalone takeover.
Priority 3 — **harden PRESENTED/COMMITTED and keep H1**: record presenter completion after original UIKit attachment/animation, match same session + controller/FBScene + window and timestamps, then yield only target SpringBoard UIWindow (not peer) before COMMITTED. Use a bounded transaction deadline grounded in measured async timing, not a single 0.85s guess; fail closed with precise rejection log. Do not tie unrelated H1 wake/peer UI lifetime to a still-pending Maps launch; retain current Home safety/watchdog and no fake owner assertion.
Priority 4 — **tests/acceptance BEFORE next DEB**: (a) saved Maps + DuoFace launch MUST remain in DuoFace, not stock Maps; (b) explicit Maps selection must either show live/touchable Maps in one pane, independent real Waze or selected peer in the other, OR reject safely with no foreground change; (c) restore the old pane if reject; (d) logo H1 one-tap recall + keyboard match previously working behavior; (e) Home, disconnect/reconnect and iOS 16.7.x owner/watchdog remain correct. Unit/CI/UIKit simulator success is necessary but not a replacement for physical vehicle evidence.
