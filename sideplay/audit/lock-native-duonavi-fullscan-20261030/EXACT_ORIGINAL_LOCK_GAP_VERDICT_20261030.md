## New precise machine-code findings, not just names in a binary

**Native12 original installs 11 distinct SpringBoard/host callbacks** in `DuoFaceDashboard.dylib`. Registration names / replacement IMPs pinned by previous original scan `native12-foreground-hooks-20261027/HOOKS_AND_ARM64.json`, and **this audit newly disassembles all 11 replacement bodies**.

1. `SBSuspendedUnderLockManager interceptUpdateForScene:withNewSettings:`, original replacement **0x2c8668**: at **0x2c86a0..0x2c86b4** loads saved original IMP `0x382120` and forwards original arguments first; then at **0x2c86c4..0x2c871c** checks `sharedInstanceIfExists` → `isUIAppBridging` → obtains scene's bundle → `shouldBridge:`. Only if it identifies a selected bridged bundle does it invoke `renderSizeForBundleID:` at **0x2c8724..0x2c8738** and continue a specific scene helper. It is **not** a blanket suppression of system transitions.
2. `SBSuspendedUnderLockManager _shouldBeBackgroundUnderLockForScene:withSettings:`, replacement **0x2c8768**: checks owner `isUIAppBridging` and policy `shouldBridge:`. When bridged live scene is recognized it executes **`mov w21,#0` at 0x2c8810**, returns FALSE without invoking original background-decision IMP. On nonmatch it follows **`ldr x8,#0x382128` at 0x2c8824 / `blr x8` at 0x2c8838**, preserving Apple's original result.
3. `SBSuspendedUnderLockManager shouldBeUnderLockForScene:`, replacement **0x2c8870**: same explicit owner+bundle guard. Recognized bridge follows **`mov w20,#0` at 0x2c8908** (FALSE), whereas unmatched scenes invoke saved system IMP **`0x382130` via `blr x8` at 0x2c892c**. This corroborates precisely WHY original treats selected live phone apps differently on physical lock while non-owned apps follow system behavior.
4. Native12 ALSO registers `FBScene updateSettings:withTransitionContext:completion:` (0x2c7e08), `FBScene _applyUpdateWithContext:completion:` (0x2c8410), `_UIScenePresentationView scene:didPrepareUpdateWithContext:` (0x2c85d0), two content-reference/orientation hooks, `SBDeviceApplicationSceneHandle` orientation support, and `SBAppViewController` update observer (0x2c8ca8) **plus destroy callback (0x2c8ef8)**. In other words, it aligns under-lock decision + scene foreground + content reference + cleanup; a lone foreground:YES setter is not equivalent.
5. **Both original signed DEBs contain independently disassembled `CBBridgeManager acquireCarPlaySleepAssertion` + `releaseCarPlaySleepAssertion`**: DuoNavi **0x1c05b8 / 0x1c0650**; Native12 **0x19eaf8 / 0x19eb90**. Both resolve `IOPMAssertionCreateWithName` (level `0xff`) and release; original signed strings say `PreventUserIdleSystemSleep`. This policy retains system activity but **does not by itself prevent display dim/off or force YouTube app's scene foreground**.
6. DuoNavi's signed dashboard shares matching CarPlay architecture `CBWindow` (`carPlayUIScreen`, `carPlayCADisplay`, `activeCarPlayWindow`, `carPlayUsableBounds`), `CBBridgeManager` (`handleCarPlayConnectionChanged:`, `performAutoResume`, `scheduleAutoResumeFallback`), and `CBBridgedUIAppView` `audioOnlyBackgroundMode`. In the original 4 Mach-O files, dashboard contains 11 sleep, 7 under-lock, 7 scene lifecycle, 24 external display and 29 video-related selector/string hits; Native12 dashboard 11 / 7 / 7 / 24 / 18 respectively. **Do not infer DuoNavi specifically installed every exact Native12 under-lock replacement from strings alone**; only Native12's 11 registration IMPs were fully proven here.

## Defect / difference in independent current DuoFace, causality tier

| Layer | Original verified | Independent DuoFace current | Confidence |
| --- | --- | --- | --- |
| Under-lock policy for explicitly bridged app scene | Native12 3 machine-code verified `SBSuspendedUnderLockManager` callbacks, source owner+bundle `shouldBridge:` guard, return 0 for owned scene, original IMP for other scenes | `DFSceneLifecycle.m` has no corresponding three under-lock owner callbacks | **Proven functional gap**, probable cause for YouTube Play failing only when phone screen off; device causality still requires same-session per-app foreground confirmation |
| Foreground/scene update | Original FBScene update **and apply** hooks + scene prepare and scene destroy handling | First-party corrects incoming foreground=NO for owned live scene and consumes observer; not equivalent coherent under-lock/scene updates | **Proven structural difference**, callback desynchronization plausible |
| CarPlay host lifetime | Original `CBWindow` and connection-aware `CBBridgeManager` with physical CarPlay display/active-window/auto-resume owner | `DFNativeHostAppDelegate.m` stops touch-owner immediately whenever CPTemplate scene `sceneWillResignActive` or `sceneDidEnterBackground`, heartbeat only while foreground-active, `DFTouchOwnerProbe.m` immediately hides all own windows and detaches after stale 2.5sec | **Proven source route** explaining black *panes* while **Apple Dock remains visible**; prior QA119 log showed matching stop/hide/restart, exact lock-button event not timestamped |
| Sleep | Both original DBs have `CBBridgeManager` IOPM request and release | First-party QA121 has matching independent API but **not built** | **Proven presence gap in signed QA120**; sleep assertion alone not sufficient to fix Play |
| Display geometry | Original native usable content measurement | QA120 native-rail X measured; user confirmed size fix on car | **Already hardware PASS by user; DO NOT change** |

**Most likely compound mechanism:** phone lock → Apple's under-lock policy backgrounds the iPhone-hosted YouTube scene because first-party bridge has not registered an equivalent narrowly scoped lock policy → video Play activation fails although a hosted view can still draw/scroll; independent CPTemplate scene lifecycle is additionally permitted to issue a stop/tombstone and hide DuoFace-owned content → Apple native Dock persists. Lighting the iPhone reactivates the phone app scene. This is a **high-priority, evidence-supported hypothesis**, not a proven precise same-tap causal trace (QA120 upload with actual lock time is still missing).
