### #8: Original evidence versus DuoFace bridge

- OmniCar original ARM64 read-only audit `chuongnguyen89dn-ui/Omnicar/audit/OmniCar_AppBridge_exact_scene_settings_and_layout_20261023.md` proves `ABHost.layoutPane:` changes scene settings frame, orientation, foreground/background via sceneHandle/sceneIfExists/updateSettingsWithBlock (original DEB SHA256 `d9297b010cdc08e401439b7332413f79cb1a056a05159a5deb673e218d76d9fd`). The dynamic functions are vendor original facts, not adopted vendor binary/license.
- CarPlayApp native Maps `DBApplicationSceneViewController` lives in its own CarPlay Dashboard UIWindow, while DuoFace physical `UIWindow` host is SpringBoard-owned. Prior source used a Dock-based two-pane plan and native UIKit adoption ACK only. An ACK does NOT establish actual maps pixels, route guidance, or physical host occupancy.
- New `DFCarPlayPhysicalPaneBinding.h` checks fresh shared session, exactly two real SpringBoard external windows, one empty target, and coordinates agreeing with CarPlay system Dock plan within 2pt. `DFNative12Chrome.m` publishes actual windows/physical->visual mapping; `DFTouchOwnerProbe.m` atomically publishes the short-lived observation; `DFNativeMapPaneCoordinator.m` rejects before adoption when invalid and verifies actual UIKit frame after adoption, rolling back mismatch.
- **NEW #8 continuation**: `DFNativeMapPaneCoordinator.m` `refreshAdoptedNativeMapBounds` runs inside the existing 0.5s owner tick only while the adapter's reversible native controller lease is alive, revalidates same session and physical window against a fresh Dock plan, and updates the actual native dashboard pane frame + hosted controller view bounds on a legitimate split-window geometry change. It does not fake new native scene resize settings or arbitrary zoom. On six consecutive missing/invalid samples (3 seconds) or unexpected owner change it restores original scene owner; on immediate size mismatch it rolls back. Real navigation still requires physical acceptance.
- Native Maps experiment supports a maximum of two visual slots, and only allows a **previously empty** DuoFace physical pane to avoid obscuring a hosted video/app. This is a deliberately stated limitation, not claim of full 3/4-map compatibility.

### #10: Functional subset and limitations

- Existing real iPhone Dock Monitor reads *actual, same-session, recent* native CarPlay Dock-owner ACK; it never toggles Dock. Existing reset is selective user-confirmed action for default/favorites and 4x2 picker, does not erase installed/approved apps or SpringBoard. Existing #4 app names show/hide and #5 reconnection restore preserved.
- NEW persisted `DFExtendedSettingsPolicy.h` offers versioned, atomic, readback-verified Vietnamese/English locale; `DFNativeHostRootController.m` allows choosing language; `DFAppPickerVC.m` uses locale for main CarPlay picker buttons/category/add-more and running action labels.
- NEW `DFVoiceAssistant.m/.h` is **first-party iPhone one-shot voice assistant**, triggered only by an explicit opt-in button on iPhone Status tab. Requests Apple's Speech recognizer and microphone permission individually; recognizes a single phrase (max 12s) in vi-VN/en-US and speaks a truthful verification of active CarPlay session, Dock ACK status, or explains experimental Maps. Never opens apps, starts mic in background, hijacks Siri or changes CarPlay Dock/scene/audio layout. The app package includes real iOS usage keys `NSSpeechRecognitionUsageDescription` and `NSMicrophoneUsageDescription` and links Speech/AVFoundation. This is **not** a replacement for system Siri/always-listening automotive assistant.
- **Outstanding unmet #10**: full localization of every legacy settings label, voice-control of media/navigation, independently auto-starting DuoFace from CarPlay Home on connecting, and forcing iPhone display off/lock without interfering with driving/safety. No unverified private UIApplication/SBBacklight call or inert placebo switch was introduced. These are not complete, and need device-specific design and consent.
