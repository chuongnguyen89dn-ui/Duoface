## What the QA176 code actually changed — confirmed static facts, unverified device effects
- Signed code source `3d0fafcc2e17bca9739cf900d0bac5668ebc1aef`, release run `42177180870` SUCCESS, public receipt `42178802321` SUCCESS. Signed audit `sideplay/jb-embedded-appbridge/evidence/runs/42177180870/audit-summary.json`: `signed=true`, `whole_deb_static_audit_pass=true`, `device_tested=false`. Public package `0.0.176~appwake1`, SHA256 `6d7cf1eff02e4c238ff0b36c93de851a834f99ef54ba2e38e19d99b50d8a0c14`. This establishes build/distribution integrity ONLY.
- `sideplay/duoface-native-scene-host/DFAppTouch177.h` now calls `if(DF176ConsumeWakeEvent(event,DF177TouchBundle))return;` **before** forwarding to the original `UIApplication sendEvent:`. That is an input-consuming change from the formerly read-only relay; its header and inline "original first / never cancels" comments are now stale. If gate conditions match, the original app touch delivery is skipped intentionally for the first event.
- `DFAppWakeGate176.h` gates on a SpringBoard-written global plist at `/var/mobile/Library/Preferences/com.duoface.nativehost.wake-state.v1.plist`, an owner pulse plist, a fresh session, exact bundle/PID and expiry. It does **not** test the `UITouch`'s screen/window/scene or CarPlay pane identity. Thus a touch in the **same app's iPhone scene** could be suppressed if its app process is eligible during an active CarPlay session. This is a **static cross-scene policy risk**, not a proven incident in QA176.
- `DFNative12Chrome.m:1256-1275`, `df176PublishWakeState`, calculates `Eligible` without checking `kbVisible177` or `kbStateKnown177`. `DF176ConsumeWakeEvent` likewise checks no keyboard visibility. Thus first input with a visible keyboard is not excluded by the gate's own policy. This is a **static keyboard-interference risk**, not yet a real-device failure finding.
- App-side `sendEvent:` synchronously reads the wake-state plist, owner pulse and (through `DFOwnerAcceptPulse`) owner/revoke evidence during a candidate first touch. No QA176 device proof exists for **app-process sandbox permission to read the SpringBoard-written files**, their freshness under suspension, or touch latency. If read fails, first-wake will silently fail open (the test never covers read failure on real iOS). This is a test gap / unverified dependency, not confirmation of sandbox denial.
- `DFNativeMapLaunchRuntime.m:141-205` replaces the older requirement that owned base view descend under `root.viewIfLoaded` with checks for exact owned controller, loaded base/root windows equal to context window, visible base alpha and controller ancestry. This can address the previously observed pre-launch rejection **if** the actual CarPlay hierarchy matches; the QA175 log does not reveal which specific new predicate will hold on the physical car. A simulated sibling-view scenario is not physical map pixel/touch proof.
