## Measured full log (read directly, no guessed events)
- **105** total `youtube-app-handshake-ack` records; all `phase=app-reflow-measured`. **0** `scene-id-unmatched` ACK records in the log. So app-side YouTube notification receiver is reachable, scene ID is accepted and callback can enumerate windows in the recorded sessions. The old diagnosis "YouTube process injection missing" is ruled out *for these ACK samples*, not necessarily for every launch.
- **17** ACKs have new .88 `normalSeen/internalSeen/layoutRefreshed` fields; the earlier **88** are the legacy ACK format without those counters. Instrumented ACKs are near file tail, lines **7211–7378**.
- All 17 instrumented ACKs show `sceneOrientation=1` (Portrait); all `normalSeen=2`; `internalSeen=2` (10 records) or `3` (7 records); `layoutRefreshed=1` in all 17. The UIKit internal-window lookup **does run** and finds windows; thus absence of internal enumerator is no longer an explanation for .88 failure.
- In these 17 ACKs **`windowsApplied=0` on 9** and **`windowsApplied=1` on 8**. This is only number of windows for which code invoked `DFYTRotate` and updated frame, **not success of YouTube player video orientation**; zero may mean the window was already the requested size/orientation or excluded by ownership/level/ABI conditions.
- Instrumented target scene sizes: `588x663` **7**, `783x663` **7**, `1175x663` **3**. Host reaches split/expanded transitions and gets updated app ACKs. No app-side `isSplit` or focus state exists in `DFYouTubeHostState.h`, and `DFHostedMapRenderSize.h` still sends a universal `round(2*pane)` geometry.
- **IMPORTANT DIRECT MISMATCH** at lines **7238–7244**: app ACK reports **`sceneOrientation=1`**, but its measured `window.rootViewController.interfaceOrientation=3` after a nominal successful `windowsApplied=1`, size **`1175x663`**. Next ACK lines **7245–7251** at the same scene size reports root controller orientation **1**. This is a real transient UIKit controller-vs-scene orientation mismatch in the app ACK; it is *not* a measurement of the YouTube video renderer or `FBScene.clientSettings`. It explains why treating `sceneOrientation=1` or `windowsApplied=1` as "video upright" is invalid.
- Host `youtube-remote-orientation-observed` appeared **57** times: all `value=1 repairEligible=0`. That log reads host `settings.interfaceOrientation`, not the app's `clientSettings.interfaceOrientation`, so the current repair condition will not run when host is Portrait but the actual controller/media presentation diverges.
- For YouTube `scene-frame-readback` appeared **96** times, all logged `same=0` as a geometry-change request was being issued; later actual sizes match previous targets. This **does not prove** scene frame updates are failing: the code logs only on its commit path, which is entered during pending changes.
- The log also shows **9** `scene-failed` events with `Scene attach exception: bogus reference size`, including **two YouTube** around lines 4864/4874 and **two Google Maps** around lines 6714/7383. These are a **separate attach/reference-size instability**, not proof of the persistent YouTube video orientation issue. Preserve Maps and .83 lifecycle; do not modify them without isolated root-cause proof.

## Corrected diagnostic conclusion
**CONFIRMED:** The host→YouTube IPC works for instrumented .88 sequences; scene owner matches and UIKit windows are being found. **CONFIRMED:** a returned ACK can claim one changed window while the root controller orientation remains landscape (3) in a Portrait scene (1). **CONFIRMED:** no code path reads and compares app-side `clientSettings.interfaceOrientation`, the known original SidePlay mechanism; `receive:` in `DFYouTubeOrientationRelay.m` only calls `apply` if owner/width/height changes or scene unavailable (plus activate/visible events). This does not represent the full Native12/DuoNavi split-mode and player presentation state machine.

**NOT CONFIRMED:** which of the two UIKit windows hosts the active video player; whether player video itself is rotated by AVKit/YouTube, whether Swipe-down is Control Center, or the precise causal event transitioning video upright. Do not mark a .89 fix or use arbitrary zoom/rotation values.
